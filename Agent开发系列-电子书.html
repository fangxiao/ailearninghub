最小可行Agent

上一期我们说了Agent的核心循环：感知、思考、行动、反思。(见OpenClaw原理篇11)

光说不练假把式。这一期，我们写一个能跑的系统。代码不到100行，但该有的循环都有。

💡 先跑起来：你看10篇原理文章，不如亲手写一个能跑的系统有感觉。

1最简版本：30行代码

先去掉所有花哨的东西，就保留最核心的循环：

import openai

class SimpleAgent:
    def __init__(self):
        self.messages = []

    def run(self, user_input):
        # 感知：把用户输入加到对话历史
        self.messages.append({"role": "user", "content": user_input})

        # 思考+行动：调用大模型
        response = openai.ChatCompletion.create(
            model="gpt-4",
            messages=self.messages
        )

        # 反思：从响应中提取助手回复
        assistant_msg = response.choices[0].message
        self.messages.append(assistant_msg)

        return assistant_msg["content"]

就这么点代码。一个类，三个方法，加起来不到30行。用法：

agent = SimpleAgent()
print(agent.run("你好"))
print(agent.run("帮我写一首诗"))

这个版本能跑，但它只是个对话机器人。Agent和普通聊天机器人的区别，在于那个"循环"。(核心循环详解)

2进阶版本：加工具调用

真正的Agent会自己决定要不要调用工具。(参考OpenClaw进阶篇09)

pythonclass SimpleAgentWithTools:
    def __init__(self):
        self.messages = []
        self.tools = {}

    def register_tool(self, name, func):
        self.tools[name] = func

    def run(self, user_input, max_turns=5):
        self.messages.append({"role": "user", "content": user_input})

        for _  in range(max_turns):
            response = openai.ChatCompletion.create(
                model="gpt-4",
                messages=self.messages,
                tools=self.tools
            )

            message = response.choices[0].message

            if message.get("tool_calls"):
                for call  in message["tool_calls"]:
                    tool_name = call["function"]["name"]
                    args = json.loads(call["function"]["arguments"])
                    result = self.tools[tool_name](**args)
                    self.messages.append({
                        "role": "tool",
                        "tool_call_id": call["id"],
                        "content": str(result)
                    })
            else:
                self.messages.append(message)
                return message["content"]

        return "已达到最大轮次"

新增三个关键点：

  • register_tool — 注册工具，让Agent知道有哪些武器可用
  • max_turns — 限制最大轮次，防止无限循环
  • tool_calls — 检测模型是否想调用工具 (参考AI Coding第28篇)

举个例子。用户问"帮我算 (12 + 8) * 3"：

  • 1. Agent想了想，发现要调用calculator
  • 2. 调用工具，算出60
  • 3. 把结果返回给用户

💡 这就是Agent的核心能力：不只是聊天，而是能真的帮你做事。

3还缺什么

这个最小版本能跑，但生产环境还差得远：

❌ 记忆系统 — 每次对话从零开始，Agent记不住之前说过什么
   (见OpenClaw原理篇12)
❌ 反思机制 — 没有判断结果对不对的能力
❌ 错误处理 — 工具调用失败了怎么办
❌ 流式输出 — 等全部生成完再返回，用户体验差

感知：用户输入到结构化意图

感知是什么？你跟Agent说"帮我订明天去上海的机票"，Agent得先理解：

  • 用户想要什么？→ 订机票
  • 出发地？→ 没说，可能是当前位置
  • 目的地？→ 上海

这个理解的过程，就是感知。把用户的自然语言，变成机器能理解的结构化数据。

💡 感知是第一步：没有这一步，Agent就是个复读机——你说啥它重复啥，不知道你要什么。

1意图识别

用户说了一句话，Agent首先要判断：用户想要做什么？这个过程叫意图识别（Intent Detection）。(参考AI Coding第28篇)

pythonINTENTS = ["订机票", "查天气", "写代码", "搜索信息", "其他"]

def detect_intent(user_input):
    prompt = f"用户说："{user_input}"\n这个用户的意图是什么？" 

    response = openai.ChatCompletion.create(
        model="gpt-4",
        messages=[{"role": "user", "content": prompt}]
    )

    return response.choices[0].message["content"]

⚠️ 但这个方法太慢了——每次都要调一次大模型。实际项目中，可以用规则匹配或者小模型来做意图识别，把大模型留到真正需要的地方。

2实体提取

判断了意图之后，还要提取关键信息。比如用户说"帮我订后天北京到上海的机票"：

  • 时间 → 后天
  • 出发地 → 北京
  • 目的地 → 上海

这个过程叫实体提取（Entity Extraction）。代码：

pythondef extract_entities(user_input):
    prompt = f"""从以下用户输入中提取关键信息：

用户输入："{user_input}"

提取以下信息（如果没有则填"未知"）：
- 时间
- 出发地
- 目的地
- 人数

请用JSON格式返回"""

    response = openai.ChatCompletion.create(
        model="gpt-4",
        messages=[{"role": "user", "content": prompt}]
    )

    import json
    return json.loads(response.choices[0].message["content"])

3整合：感知的完整实现

pythondef perceive(self, user_input):
    # 1. 识别意图
    intent = self.detect_intent(user_input)

    # 2. 提取实体
    entities = self.extract_entities(user_input)

    # 3. 组合成结构化上下文
    return {
        "intent": intent,
        "entities": entities,
        "raw_input": user_input
    }

💡 感知做好了：后面的思考和行动就轻松了。Agent知道你要什么，才能决定怎么做。

思考：Agent是怎么"想"的

上一期我们说了感知。用户说了一句话，Agent知道用户想要什么了。

接下来是思考。感知知道了你要什么，思考来决定怎么做。(见OpenClaw原理篇11)

思考听起来很玄乎。但在大模型时代，思考其实就是一次大模型的调用。模型根据你的问题和上下文，决定下一步该做什么。

💡 核心观点：所谓的"思考"，本质上是让大模型根据当前情况，决定是调用工具、收集更多信息，还是直接回答。

1ReAct模式

最常用的思考模式叫ReAct——Reasoning + Acting。就是一边推理，一边行动。

举个例子。用户问："帮我查一下上海今天的天气，如果下雨就别出门了。"

Agent的思考过程是这样的：

  1. 思考：我需要先查天气，才能回答用户的问题
  2. 行动：调用天气查询工具
  3. 观察：查询结果是今天上海有雨
  4. 思考：用户说下雨就别出门，我应该建议用户今天不要出门

Figure: ReAct Loop - Thought -> Action -> Observation -> Thought

思考：我需要先查天气，才能回答用户的问题
  ↓
行动：调用天气查询工具
  ↓
观察：查询结果是今天上海有雨
  ↓
思考：用户说下雨就别出门，建议用户不要出门

3Chain of Thought

还有一个概念叫Chain of Thought，思维链。就是让模型把思考过程说出来，而不只是给结论。

💡 实践经验：让模型"解释一下你是怎么想的"，往往能得到更准确的答案。

知道了Agent是怎么"想"的，接下来我们来说说它是怎么"做"的——行动。

行动：工具是怎么被调用的

思考完了，下一步就是行动。行动就是调用工具。(参考OpenClaw进阶篇09)

💡 核心观点：Agent能做什么事，就看它有多少工具。工具越多，能力越强。(参考AI Coding第29篇)

2工具执行

拿到函数名和参数之后，下一步就是执行：

pythondef execute_tool(self, tool_name, args):
    tool_func = self.tools.get(tool_name)

    if tool_func  is None:
        return f"找不到工具：{tool_name}"

    try:
        result = tool_func(**args)
        return result
    except Exception as e:
        return f"工具执行出错：{str(e)}"

3结果返回

工具执行完了，要把结果传回给模型，让模型决定下一步怎么做：

python# 执行工具
tool_result = self.execute_tool(function_name, arguments)

# 把结果加到消息历史
self.messages.append({
    "role": "tool",
    "tool_call_id": tool_call["id"],
    "content": str(tool_result)
})

# 再次调用模型，让它处理工具返回的结果
response = openai.ChatCompletion.create(
    model="gpt-4",
    messages=self.messages
)

💡 完整流程：模型决定调用 → 传递参数 → 执行工具 → 返回结果 → 模型继续处理。

反思：Agent是怎么"反省"的

上一期我们说了行动。Agent调用了工具，拿到了结果。

然后呢？然后就结束了吗？

不是。Agent还需要反思：这次做得怎么样？结果对不对？要不要重来一次？(见OpenClaw原理篇11)

💡 核心观点：反思是Agent自我纠错的关键。没有反思，Agent就会"一条道走到黑"，不管结果对不对都继续执行。

1为什么要反思

举个例子。用户让Agent帮他写一封邮件。Agent调用工具写完了，把结果返回给用户。

但用户可能不满意——语气太正式了，或者遗漏了什么信息。

如果没有反思环节，Agent就只会机械地执行任务，不会自我改进。加上反思，Agent才能知道自己的不足，然后调整策略、重新尝试。

Figure: Agent Reflection Flow - Action -> Check -> Judge -> Adjust

2代码实现

反思的核心是判断结果是否正确。简单来说，就是问自己几个问题：

  • 工具调用成功了吗？
  • 返回的结果合理吗？
  • 用户的问题解决了吗？
  • 要不要重试？

代码大概是这样：

pythondef reflect(self, context, result):
    if result.is_error:
        return {
            "success": False,
            "reason": "工具调用出错",
            "retry": True,
            "strategy": "换工具或换参数"
        }

    if not self.validate_result(result):
        return {
            "success": False,
            "reason": "结果验证失败",
            "retry": True,
            "strategy": "调整参数重试"
        }

    if not self.is_task_done(context, result):
        return {
            "success": False,
            "reason": "任务未完成",
            "retry": True,
            "strategy": "继续执行下一步"
        }

    return {
        "success": True,
        "reason": "任务完成",
        "retry": False,
        "strategy": None
    }

💡 实践要点：反思就是让Agent"回头看"：这次做得怎么样？要不要调整？要不要重试？

3反思的粒度

反思可以做得很简单，也可以做得复杂。

级别 做法 适用场景
简单版 检查工具调用有没有报错 快速原型、简单任务
中等版 检查返回结果是否合理 一般业务场景
复杂版 让大模型判断结果质量 对准确性要求高的任务

⚠️ 建议：实际项目中，可以先做简单版，再慢慢加复杂逻辑。过早追求复杂的反思机制，往往是过度设计。

说完反思，接下来我们来说说记忆系统——Agent是怎么记住之前说过的话的。

记忆系统：Agent是怎么"记住"东西的

之前我们写的最小可行Agent，有个问题：每次对话都是从零开始。(见OpenClaw原理篇12)

你跟它说"帮我写一封邮件"，它写完了。你再说"把语气改得更正式一点"，它不知道你说的是哪封邮件，因为它记不住。

记忆系统就是来解决这个问题的。Agent需要记住之前说过的话、做过的事，这样才能连续对话。

💡 核心观点：没有记忆的Agent，每次对话都是"陌生人"。记忆让Agent能认识"回头客"。

1四层记忆架构

一般来说，Agent的记忆分四层：(参考AI Coding第28篇)

第一层：对话历史（短期记忆）

记录当前对话的内容。对话结束就消失。每次API调用都会带上。

第二层：实体记忆（中期记忆）

记录用户的基本信息，比如姓名、偏好、常驻城市。跨对话保持。

第三层：知识记忆（长期记忆）

Agent从训练中学会的知识，或者从外部检索来的信息。

第四层：技能记忆

Agent学会的技能，比如怎么写代码、怎么分析数据。

2代码实现

最简单的记忆系统，就是把对话历史存起来，每次调用的时候带上：

pythonclass AgentWithMemory:
    def __init__(self):
        self.messages = []
        self.entities = {}

    def add_message(self, role, content):
        self.messages.append({"role": role, "content": content})

    def add_entity(self, key, value):
        self.entities[key] = value

    def build_context(self):
        context = []
        
        if self.entities:
            entity_prompt = "你知道以下关于用户的信息："
            for key, value  in self.entities.items():
                entity_prompt += f"\n- {key}：{value}"
            context.append({"role": "system", "content": entity_prompt})
        
        context.extend(self.messages)
        return context

用起来是这样的：

💡 实践要点：记忆系统让Agent能"记住"用户说过的话、做过的操作。这样它才能真正帮你完成任务，而不是每次都从零开始。

3记忆的管理

记忆多了会有问题。上下文窗口是有限的，存太多东西API会爆。

策略 做法 适用场景
定期压缩 把多轮对话压缩成摘要 长对话场景
重要性筛选 只保留重要的信息 信息繁多的场景
向量检索 把记忆向量化，需要时检索 大规模记忆存储
分层存储 短期记忆放内存，长期记忆放数据库 需要持久化的场景

⚠️ 注意事项：不是记忆越多越好。有效的记忆管理比盲目存储更重要。

│ ·结果返回   │
└─────────────┘
    ↓
┌─────────────┐
│ 反思层     │
│ ·结果校验   │
│ ·错误处理   │
│ ·策略调整   │
└─────────────┘
    ↓
回答用户 / 继续循环

这是一个循环，不是一次性的流程。Agent会不断在思考层和行动层之间循环，直到任务完成或者达到最大循环次数。

2四层职责回顾

层次 输入 输出 核心问题
感知 用户原始输入 结构化意图+实体 用户真正想要什么？
思考 意图+上下文 行动决策 我应该怎么做？
行动 决策+工具列表 执行结果 工具返回了什么？
反思 执行结果 校验+策略调整 结果对吗？需要重试吗？

3ReAct循环：思考与行动的交替

ReAct是现在最主流的Agent思考模式。(参考AI Coding第28篇)

它的核心是： Thought → Action → Observation → Thought → Action...

pythonasync def run(self, user_input: str, max_turns: int = 10):
    messages = [{"role": "user", "content": user_input}]

    for turn in range(max_turns):
        # 1. 思考：让模型决定下一步
        response = await self.llm.chat(messages, tools=self.tools)

        # 2. 如果没有工具调用，直接返回
        if not response.tool_calls:
            messages.append(response)
            return response.content

        # 3. 执行工具
        for tool_call in response.tool_calls:
            result = await self.llm.execute_tool(tool_call)
            messages.append({
                "role": "tool",
                "tool_call_id": tool_call.id,
                "content": str(result)
            })

        # 4. 反思：检查是否需要继续
        if self.is_complete(messages):
            break

    return "已达到最大循环次数"

这个循环会一直持续，直到：

  • 模型认为任务完成，不再调用工具
  • 达到最大循环次数（防止无限循环）
  • 出现无法恢复的错误

4工具调用是桥梁

思考和行动之间，工具调用是桥梁。(参考OpenClaw进阶篇09)

模型生成tool_calls，我们负责执行，然后把结果传回去。这个设计非常精妙：

  • 模型不需要知道工具怎么执行——只管"调用"就行
  • 我们不需要写复杂的决策逻辑——让模型自己决定
  • 扩展性极强——加一个新工具，模型就能用

5反思让Agent更可靠

没有反思的Agent，就像一个不会复盘的人——犯了错不知道改，同样的错误会一直犯。(参考AI Coding第29篇)

反思层要做的事情：

  1. 结果校验——工具返回的结果是否符合预期？
  2. 错误处理——出错了是重试还是换策略？
  3. 策略调整——这个方法不行，要不要试试别的？
pythondef reflect(self, tool_result, context):
    # 检查工具执行是否出错
    if is_error(tool_result):
        if is_retryable(tool_result):
            return "retry"  # 可重试的错误，重试一次
        else:
            return "fail"   # 不可重试的错误，直接失败

    # 检查结果是否符合预期
    if not self.is_satisfactory(tool_result, context):
        return "replan"  # 结果不满意，需要重新规划

    return "continue"  # 一切正常，继续执行

6核心循环的意义

理解了核心循环，你能做到很多事情：

  • 调试Agent——当Agent行为不符合预期，你能定位是哪一层出了问题
  • 优化Agent——知道哪层薄弱，就重点优化哪层
  • 设计新Agent——不管什么场景，都可以用这个框架来思考

💡 总结：Agent的核心循环是"感知→思考→行动→反思"的无限循环。ReAct模式让模型自己决定下一步做什么。工具调用是思考和行动的桥梁。反思让Agent能自我纠错。这个循环理解透了，Agent开发就学会了一半。

四层记忆架构

上一期我们说了反思。Agent能判断结果对不对，能调整策略。

但还有一个问题没解决：Agent是怎么记住之前说过的话的？(见OpenClaw原理篇12)

这就是记忆系统要解决的问题。

💡 核心观点：没有记忆的Agent，每次对话都是"陌生人"。记忆让Agent能认识"回头客"。

1为什么需要记忆

之前我们写的最小可行Agent，有个问题：每次对话都是从零开始。

你跟它说"帮我写一封邮件"，它写完了。你再说"把语气改得更正式一点"，它不知道你说的是哪封邮件，因为它记不住。

记忆系统就是来解决这个问题的。Agent需要记住之前说过的话、做过的事，这样才能连续对话。

2四层记忆架构

一般来说，Agent的记忆分四层：(参考AI Coding第28篇)

第一层：对话历史（短期记忆）

记录当前对话的内容。对话结束就消失。每次API调用都会带上。

第二层：实体记忆（中期记忆）

记录用户的基本信息，比如姓名、偏好、常驻城市。跨对话保持。

第三层：知识记忆（长期记忆）

Agent从训练中学会的知识，或者从外部检索来的信息。

第四层：技能记忆

Agent学会的技能，比如怎么写代码、怎么分析数据。

3代码实现

最简单的记忆系统，就是把对话历史存起来，每次调用的时候带上：

pythonclass AgentWithMemory:
    def __init__(self):
        self.messages = []
        self.entities = {}

    def add_message(self, role, content):
        self.messages.append({"role": role, "content": content})

    def add_entity(self, key, value):
        self.entities[key] = value

    def build_context(self):
        context = []
        
        if self.entities:
            entity_prompt = "你知道以下关于用户的信息："
            for key, value  in self.entities.items():
                entity_prompt += f"\n- {key}：{value}"
            context.append({"role": "system", "content": entity_prompt})
        
        context.extend(self.messages)
        return context

agent.add_message("user", "改成后天的")

💡 实践要点：记忆系统让Agent能"记住"用户说过的话，做过的操作。这样它才能真正帮你完成任务，而不是每次都从零开始。

4记忆的管理

记忆多了会有问题。上下文窗口是有限的，存太多东西API会爆。

策略 做法 适用场景
定期压缩 把多轮对话压缩成摘要 长对话场景
重要性筛选 只保留重要的信息 信息繁多的场景
向量检索 把记忆向量化，需要时检索 大规模记忆存储
分层存储 短期记忆放内存，长期记忆放数据库 需要持久化的场景

⚠️ 注意事项：不是记忆越多越好。有效的记忆管理比盲目存储更重要。

说完四层记忆架构，接下来我们来说说具体怎么管理这些记忆——上下文窗口管理。

上下文窗口管理

记忆系统让Agent能记住东西了。但还有一个问题：上下文窗口是有限的。

GPT-4的上下文窗口有128K tokens听起来很大，但实际用起来很快就会塞满。特别是处理长文档、进行多轮对话的时候。

💡 核心观点：上下文窗口管理，就是在有限的窗口内塞进最多的有效信息。

1滑动窗口

最简单的方法是滑动窗口。只保留最近N条消息，超出的就丢掉。

pythonclass SlidingWindowMemory:
    def __init__(self, max_messages=10):
        self.messages = []
        self.max_messages = max_messages

    def add(self, role, content):
        self.messages.append({"role": role, "content": content})
        
        if len(self.messages) > self.max_messages:
            self.messages = self.messages[-self.max_messages:]

    def get_messages(self):
        return self.messages

缺点也很明显：早天的对话会被完全丢掉。如果用户说"接着上次说的继续写"，Agent可能完全不记得上次说了什么。

2摘要压缩

更好的方法是摘要压缩。当对话太长时，把之前的对话压缩成摘要。

pythonclass SummarizingMemory:
    def __init__(self, max_tokens=4000):
        self.summary = ""
        self.recent_messages = []
        self.max_tokens = max_tokens

    def add(self, role, content):
        self.recent_messages.append({"role": role, "content": content})

        if self.count_tokens(self.recent_messages) > self.max_tokens:
            self.compress()

    def compress(self):
        prompt = f"""请把以下对话压缩成一段摘要：
{self.recent_messages}
摘要应该包含：1) 主要话题 2) 用户的关键需求 3) 任何重要决定或结论"""

        response = openai.ChatCompletion.create(
            model="gpt-4",
            messages=[{"role": "user", "content": prompt}]
        )

        self.summary = response.choices[0].message["content"]
        self.recent_messages = []

    def get_context(self):
        context = []
        if self.summary:
            context.append({"role": "system", "content": f"之前的对话摘要：{self.summary}"})
        context.extend(self.recent_messages)
        return context

除了压缩，还有一些小技巧可以节省token：

技巧 做法 节省比例
缩短系统提示 把重复性的指示压缩 10-20%

3RAG实战

Figure: RAG Flow - Query -> Vector Search -> Retrieve -> LLM -> Answer

RAG的流程是这样的：

  1. 把知识文档切成小块，存入向量数据库
  2. 用户提问时，先在向量数据库里检索相关的内容
  3. 把检索到的内容和用户问题一起发给大模型
  4. 大模型基于这些内容生成答案
pythonclass RAGAgent:
    def __init__(self, vector_store):
        self.vector_store = vector_store

    def retrieve(self, query, top_k=3):
        results = self.vector_store.query(query, top_k)
        return results['documents']

    def answer(self, question):
        relevant_docs = self.retrieve(question)
        context = "\n".join(relevant_docs)

        prompt = f"""基于以下信息回答问题。如果信息不足，请说明你不知道。

信息：
{context}

问题：{question}
答案："""

        response = openai.ChatCompletion.create(
            model="gpt-4",
            messages=[{"role": "user": content, "content": prompt}]
        )

        return response.choices[0].message["content"]

💡 RAG的优势：1) 可以处理超长文档 2) 答案有据可查 3) 可以实时更新知识库 4) 节省token

实战：让Agent记住你是谁

1需求分析

我们要实现以下功能：

  • 记住用户的姓名、联系方式、偏好等基本信息
  • 跨对话保持记忆（重启程序后不丢失）
  • 能根据记忆提供个性化服务

2完整代码

pythonimport json
import os

class PersistentMemoryAgent:
    def __init__(self, memory_file="user_memory.json"):
        self.memory_file = memory_file
        self.memory = self.load_memory()
        self.messages = []

    def load_memory(self):
        if os.path.exists(self.memory_file):
            with open(self.memory_file, 'r') as f:
                return json.load(f)
        return {"user_info": {}, "preferences": {}, "history": []}

    def save_memory(self):
        with open(self.memory_file, 'w') as f:
            json.dump(self.memory, f, ensure_ascii=False, indent=2)

    def update_memory(self, key, value):
        if "user_info"  in key:
            self.memory["user_info"][key] = value
        else:
            self.memory["preferences"][key] = value
        self.save_memory()

    def build_context(self):
        context = []
        
        user_info = self.memory.get("user_info", {})
        if user_info:
            info_text = "用户信息："
            for k, v  in user_info.items():
                info_text += f"\n- {k}：{v}"
            context.append({"role": "system", "content": info_text})

        context.extend(self.messages[-10:])
        return context

    def chat(self, user_input):
        self.messages.append({"role": "user", "content": user_input})
        
        response = openai.ChatCompletion.create(
            model="gpt-4",
            messages=self.build_context()
        )

        answer = response.choices[0].message["content"]
        self.messages.append({"role": "assistant", "content": answer})
        return answer

Tool接口设计

之前我们说了记忆系统。Agent能记住东西了，下一步是让它能"做事"。

这一篇，我们来说说Tool接口设计——怎么让Agent调用工具。(参考OpenClaw进阶篇09)

💡 核心观点：Agent能做什么事，取决于它有多少工具。好的Tool接口设计，让扩展工具变得简单。

1为什么需要统一的接口

想象一下，如果没有统一的接口，每个工具都得单独写调用代码。搜索要写一套、计算器要写一套、发邮件又要写一套。

有了统一的Tool接口，所有工具都遵循同样的规范。注册、调用、返回结果，都是一套代码。

2Tool基类

pythonfrom abc import ABC, abstractmethod
from typing import Any, Dict

class BaseTool(ABC):
    """所有工具的基类"""

        def name(self) -> str:
        """工具名称，Agent通过这个名字调用"""
        raise NotImplementedError

        def description(self) -> str:
        """工具描述，让模型知道什么时候该用"""
        raise NotImplementedError

        def parameters(self) -> Dict:
        """参数schema，用于Function Calling"""
        raise NotImplementedError

        def execute(self, **kwargs) -> Any:
        """实际执行工具逻辑"""
        pass

3参数校验

参数校验很重要。不能让Agent传给工具的参数是乱七八糟的。

pythonfrom pydantic import BaseModel, ValidationError

class WeatherInput(BaseModel):
    city: str
    date: str = "today"

class WeatherTool(BaseTool):
    @property
    def name(self): return "get_weather"

    @property
    def description(self):
        return "查询指定城市的天气"

    @property
    def parameters(self):
        return {
            "type": "object",
            "properties": {
                "city": {"type": "string", "description": "城市名称"},
                "date": {"type": "string", "description": "日期，默认为today"}
            },
            "required": ["city"]
        }

    def execute(self, city, date="today"):
        try:
            WeatherInput(city=city, date=date)
        except ValidationError:
            return "参数错误：城市名称不能为空"
        return f"{city} {date}的天气：晴，25度"

3依赖分析与并行规划

分解后的子任务，有些可以并行执行，有些必须按顺序执行。

pythonclass TaskScheduler:
    def create_execution_plan(self, tasks):
        # 构建依赖图
        graph = {t["id"]: t.get("depends_on", []) for t in tasks}

        # 找出可以并行的任务
        plan = []
        completed = set()

        while len(completed) < len(tasks):
            # 找出所有依赖都已完成的任务
            ready = []
            for task in tasks:
                tid = task["id"]
                if tid in completed:
                    continue
                if all(dep in completed for dep in graph[tid]):
                    ready.append(task)

            if not ready:
                break  # 环形依赖

            plan.append(ready)
            for t in ready:
                completed.add(t["id"])

        return plan  # [[task1, task2], [task3]] 表示可并行，执行顺序

1回滚机制

当某个子任务失败时，需要回滚已完成的操作，保持系统状态一致。

pythonclass RollbackManager:
    def __init__(self):
        self.history = []

    def save_state(self, state):
        self.history.append(state)

    def rollback(self):
        if not self.history:
            return None
        state = self.history.pop()
        return state

    def handle_failure(self, failed_task, context):
        # 回滚到上一个稳定状态
        previous_state = self.rollback()
        if previous_state:
            context.restore(previous_state)
        return {
            "action": "replan",
            "reason": f"Task {failed_task} failed"
        }

消息总线

多Agent协作需要一个通信中枢。消息总线就是扮演这个角色——它让Agent之间的消息传递变得可靠、可追踪。

💡 核心观点：消息总线是Agent系统的"神经系统"，负责消息路由、事件分发和状态同步。

1消息类型

pythonfrom enum import Enum

class MessageType(Enum):
    TASK = "task"           # 任务分配
    RESULT = "result"       # 结果返回
    EVENT = "event"         # 事件通知
    QUERY = "query"         # 状态查询
    BROADCAST = "broadcast"   # 广播消息

class Message:
    def __init__(self, msg_type, sender, content, target=None):
        self.type = msg_type
        self.sender = sender
        self.target = target
        self.content = content
        self.timestamp = datetime.now()
        self.id = uuid.uuid4().hex()

2消息总线实现

pythonclass MessageBus:
    def __init__(self):
        self.subscribers = {}
        self.message_queue = Queue()
        self.message_history = []

    def subscribe(self, agent, msg_types):
        for msg_type in msg_types:
            if msg_type not in self.subscribers:
                self.subscribers[msg_type] = []
            self.subscribers[msg_type].append(agent)

    def publish(self, message):
        self.message_history.append(message)
        self.message_queue.put(message)

    def dispatch(self):
        while not self.message_queue.empty():
            message = self.message_queue.get()
            targets = self.subscribers.get(message.type, [])
            for target in targets:
                target.receive(message)

    def send(self, from_agent, to_agent, content):
        msg = Message(MessageType.TASK, from_agent, content, to_agent)
        self.publish(msg)

pythonclass ResultAggregator:
    def aggregate(self, results, strategy="merge"):
        if strategy == "merge":
            return self.merge_results(results)
        elif strategy == "chain":
            return self.chain_results(results)
        elif strategy == "vote":
            return self.vote_results(results)

    def merge_results(self, results):
        merged = {}
        for task_id, result in results.items():
            merged.update(result)
        return merged

    def chain_results(self, results):
        ordered = sorted(results.items(), key=lambda x: x[0])
        output = ""
        for _, result in ordered:
            output += result.get("content", "")
        return {"content": output}

    def vote_results(self, results):
        votes = Counter()
        for result in results.values():
            answer = result.get("answer")
            votes[answer] += 1
        return {"answer": votes.most_common(1)[0][0]}

class AsyncExecutionEngine:
    def __init__(self, max_workers=10):
        self.executor = ThreadPoolExecutor(max_workers=max_workers)

    async def execute_parallel(self, tasks):
        loop = asyncio.get_event_loop()
        futures = [
            loop.run_in_executor(self.executor, task)
            for task in tasks
        ]
        results = await asyncio.gather(*futures)
        return results

    async def execute_batch(self, batch):
        # 同一批次的任务可以并行执行
        return await self.execute_parallel(batch)

class ResultCache:
    def __init__(self, max_size=1000):
        self.cache = {}
        self.max_size = max_size

    def _make_key(self, task):
        # 基于任务内容生成缓存key
        content = str(task.get("task")) + str(task.get("context"))
        return hashlib.md5(content.encode()).hexdigest()

    def get(self, task):
        key = self._make_key(task)
        return self.cache.get(key)

    def set(self, task, result):
        if len(self.cache) >= self.max_size:
            # LRU淘汰
            self.cache.pop(next(iter(self.cache)))
        key = self._make_key(task)
        self.cache[key] = result

可观测性

Agent系统上线后，怎么知道它运行得好不好？有没有出问题？

传统软件出了问题，可以看日志、查数据库。但Agent系统复杂在哪？它涉及多次LLM调用、工具执行、多步骤推理——一个请求可能跨十几个服务、产生上百条日志。

可观测性就是回答这些问题的：我的Agent在想什么？它为什么这么做？哪里出了问题？

核心观点：可观测性三板斧——日志（Log）记录事件、指标（Metrics）反映趋势、追踪（Trace）串联调用链。做好这三点，生产环境的问题无处遁形。

1日志设计：让Agent的每一步都有迹可循

日志是排查问题的第一手资料。但Agent的日志和普通系统不同——我们需要记录的不仅是"系统发生了什么"，还要记录"Agent在想什么"。

看这段日志设计：

2指标采集：让趋势一目了然

日志告诉你"发生了什么"，但如果你想知道"最近怎么样"、"有没有异常趋势"，就需要指标了。

指标分三种类型：

类型 说明 举例
Counter（计数器） 只增不减，记录累计数量 总请求数、任务完成数
Gauge（仪表） 可增可减，记录瞬时值 当前活跃任务数、队列长度
Histogram（直方图） 记录分布情况 响应时间分布、Token消耗分布 
pythonclass MetricsCollector:
    def __init__(self):
        self.counters = {}
        self.gauges = {}
        self.histograms = {}

    def increment(self, name, value=1):
        self.counters[name] = self.counters.get(name, 0) + value

    def gauge(self, name, value):
        self.gauges[name] = value

    def histogram(self, name, value):
        if name not in self.histograms:
            self.histograms[name] = []
        self.histograms[name].append(value)

    def get_metrics(self):
        return {
            "counters": self.counters,
            "gauges": self.gauges,
            "histograms": {
                k: {"count": len(v),
                   "avg": sum(v)/len(v) if v else 0
                }
                for k, v in self.histograms.items()
            }
        }

    def export_to_prometheus(self):
        lines = []
        for name, value in self.counters.items():
            lines.append(f"agent_counter{name=\"{name}\"} {value}")
        for name, value in self.gauges.items():
            lines.append(f"agent_gauge{name=\"{name}\"} {value}")
        return "\n".join(lines)

1AutoGPT

AutoGPT是最早的Agent框架之一，核心理念是"自主Agent"——给定目标，Agent自己思考、分解、执行。

class AutoGPT:
    def think(self, goal):
        # 1. 分析目标，生成任务列表
        tasks = self.decompose(goal)

        # 2. 逐个执行任务
        for task in tasks:
            result = self.execute(task)
            self.review(result)  # 自我审查

        # 3. 如果目标没达成，重新规划
        if not self.goal_achieved():
            self.think(goal)  # 递归

4Agent开发的六个关键认知

这30篇文章里，我最想传递的，不是某个具体实现，而是六个关键认知：

认知一：Agent不是魔法
Agent的本质是一个循环执行的系统：感知输入 → 思考决策 → 调用工具 → 观察结果 → 继续循环。它之所以看起来"智能"，是因为大模型提供了强大的理解能力。

认知二：Prompt是接口，不是指令
很多人把Prompt当成"命令"来写，其实Prompt是接口设计。好的Prompt要定义清楚：Agent是谁、要做什么、怎么做、边界在哪。

认知三：记忆是有代价的
上下文窗口是有限的，Token是花钱的。记忆系统设计的目标是：在有限资源下，让Agent记住最该记住的。

认知四：工具调用是双刃剑
工具让Agent能力边界极大扩展，但也带来了错误放大的风险。Agent执行100步，只要一步出错，结果就可能偏离。所以工具设计要简洁、安全、有边界。

认知五：多Agent不是银弹
多Agent看起来很美——分工明确、各司其职。但协作成本很高：消息协议、状态同步、结果冲突……很多场景下，单Agent反而更简单有效。

认知六：工程能力决定落地
Prompt调得再好，生产环境跑不起来也是白搭。可观测性、容错机制、资源控制……这些"不性感"的东西，才是Agent能否上线的关键。
