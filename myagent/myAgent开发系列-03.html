技术选型：为什么用现在的技术栈

每次技术分享会，都有人问我：为什么你们选这个技术？为什么不选那个？

今天系统性地解答一下。技术选型不是选最新的，而是选最合适的。脱离场景谈技术好坏，都是耍流氓。

💡 核心观点：技术选型的核心是"够用就行"。过度设计是浪费，不足设计是隐患。myAgent的目标是学习和轻量定制，所以选型的原则是：最小依赖、最快上手、最易调试。

1前端：Next.js + TypeScript

先说前端。很多人问：为什么不用Vue？为什么不用纯React？

Next.js 14 (App Router)是我目前最推荐的React框架。为什么？

  • SSR/SSG一把梭——不管是做SEO页面还是做API动态页面，一套架构搞定
  • Server Components——减少客户端JS，提升首屏加载速度
  • API Routes——前后端可以放在一个项目里，学习成本最低
text# Next.js 14 项目结构
app/
├── page.tsx           # 页面组件（Server Component）
├── api/
│   └── bots/          # API Routes
├── bots/
│   └── [id]/
│       └── page.tsx   # Bot详情页
└── layout.tsx        # 根布局

TypeScript是必选的。有人觉得TypeScript增加学习成本，但减少的debug时间远大于增加的学习时间。尤其是团队协作时，类型即文档，看类型就知道函数该怎么用。

为什么不用Vue？Vue3的Composition API很好，但Next.js的生态更成熟，AI相关的组件库支持更好。比如Vercel官方出的AI SDK，就是为Next.js量身定制的。

2后端：Python + FastAPI

后端选Python 3.11+ + FastAPI，这个组合在AI领域几乎是标配。

为什么是Python？

  • AI生态碾压一切——LangChain、AutoGen、LlamaIndex，全是Python先支持
  • 数据处理方便——Agent场景大量JSON/文本处理，Python字典比Node.js对象方便太多
  • 异步支持好——Python 3.11+的asyncio已经非常成熟

为什么是FastAPI而不是Django或Flask？

text# FastAPI vs Django vs Flask
#
# Django: 太重，ORM那套对Agent场景没用，自带admin后台根本用不上
# Flask: 太轻，缺乏类型提示，写大项目容易变成面条代码
# FastAPI: 刚刚好，类型提示完善，异步支持好，自动文档生成

# FastAPI示例
from fastapi import FastAPI
from pydantic import BaseModel

class BotCreate(BaseModel):
    name: str
    description: str | None = None

# 自动生成OpenAPI文档，类型检查，异步支持 —— 全有了

FastAPI的自动文档生成功能简直是开发神器。打开/docs就能看到完整的API文档，还能直接在线调试。后端写完，前端对着文档就能联调，不用专门开会对接口。

3数据库：PostgreSQL + Redis

数据库选型是争议最大的。有人觉得PostgreSQL太重，有人觉得MongoDB更灵活。

我的观点：结构化数据用PostgreSQL，缓存用Redis，向量检索用pgvector扩展。

场景选型原因
用户、Bot配置PostgreSQL强类型、事务支持好
Session、缓存Redis高性能，TTL支持好
向量检索pgvector一体化，不需要额外服务
日志、监控PostgreSQL不需要专门搭ELK

为什么不用MongoDB？

  • MongoDB的JSON存储看起来灵活，但实际上缺少强类型约束，数据质量难以保证
  • Agent场景的数据，其实大部分是有结构的——Bot配置、用户信息、对话记录，用PostgreSQL的JSONB字段完全够用
  • pgvector一体化是加分项，别的数据库做不到

为什么不用Pinecone等专用向量数据库？

  • pgvector够用——百万级向量完全没问题
  • 少一个外部依赖——部署复杂度降低一半
  • 一致性好——所有数据在一个数据库，事务保证更强

4工具链：Docker Compose一把梭

部署工具选Docker Compose，而不是直接上Kubernetes。

不是K8s不好，是大多数场景用不上。

yaml# docker-compose.yml
services:
  frontend:
    build: ./frontend
    ports:
      - "3000:3000"
    depends_on:
      - backend

  backend:
    build: ./backend
    ports:
      - "8000:8000"
    environment:
      - DATABASE_URL=postgresql://...
      - REDIS_URL=redis://...

  postgres:
    image: pgvector/pgvector:pg15
    # 一个镜像同时跑PostgreSQL和向量检索

  redis:
    image: redis:7-alpine

docker-compose up就能跑完整环境，没有任何高深概念。等项目大了，需要水平扩展了，再考虑迁移到K8s也不迟。

5技术选型的反面教材

说完了为什么选这些，再说说常见反面教材。

反面教材1：追新党

"我要用最新的Rust做后端！"、"我要用最新发布的D1数据库！"

新技术当然好，但新技术的坑你踩得起吗？文档不完善、周边库少、出了问题Google搜不到答案。生产环境出问题，老板可不会听你解释"这是新技术嘛"。

反面教材2：全能党

"既然要微服务，那就拆20个Docker容器吧！"

一个Bot平台，你需要独立部署的容器有：frontend、backend、postgres、redis。够了。非要把message queue拆出来、非要把logger拆出来、每个模块一个容器——这是过度设计。

反面教材3：权威党

"Google用K8s，所以我们也要用K8s！"、"字节跳动用Go，我们也要用Go！"

脱离场景谈技术，都是耍流氓。Google的流量是每秒亿级，你的流量是每秒百级。抄架构不是抄作业，场景不同，方案完全不同。

💡 总结：myAgent的技术栈是：Next.js + TypeScript + FastAPI + PostgreSQL + Redis + pgvector + Docker Compose。选型原则是"够用就行，最小依赖"。不追新，不追大公司方案，只选最适合学习和小规模部署的组合。
