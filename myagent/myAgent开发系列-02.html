模块边界与通信机制

上一期我们讲了四层架构，但架构只是蓝图。真正的问题是：这些层之间怎么通信？模块之间怎么解耦？

我见过太多"一开始写得爽，后来改一行代码崩整个系统"的惨案。问题出在哪？模块边界没划清楚。

💡 核心观点：好的架构不是"怎么代码写得多漂亮"，而是"将来改需求的时候能不能只改一个地方"。模块边界划清楚，是这一切的基础。

1myAgent有哪几个核心模块？

拆开myAgent，内部其实就四个核心模块：

模块职责类比
Bot模块Bot的创建、配置、版本管理一个活的AI助手
插件模块工具扩展、第三方能力接入给助手装上各种技能
工作流模块流程编排、多步骤任务执行帮助手规划复杂任务
记忆模块对话历史、知识存储、上下文助手的大脑

这四个模块，理论上可以独立开发、独立测试、独立部署。但它们又不是完全隔离的——需要通信。

2模块间通信：事件驱动架构

模块之间怎么通信？最笨的办法是直接调用：

python# 耦合的写法 —— 不要这样做
class Bot:
    def execute(self):
        memory = Memory()      # 直接创建
        plugin = Plugin()      # 直接创建
        workflow = Workflow()  # 直接创建
        # ... 几十个直接调用

这种写法，短期爽，长期痛苦。某天你要把Memory换成另一个实现？改到吐血。

正确做法是事件驱动 + 依赖注入：

python# 解耦的写法 —— 事件总线模式
class EventBus:
    # 单例，全局事件总线
    _subscribers: Dict[str, List[Callable]] = {}

    def subscribe(self, event_type: str, handler: Callable):
        if event_type not self._subscribers:
            self._subscribers[event_type] = []
        self._subscribers[event_type].append(handler)

    def publish(self, event: "Event"):
        for handler in self._subscribers.get(event.type, []):
            handler(event)

事件驱动的核心思想是：模块之间不直接调用，而是通过"发布事件"来通信。谁关心谁订阅，不需要的模块完全无感知。

3事件类型：哪些事件需要全局通信？

myAgent内部有这几类核心事件：

事件触发时机谁关心
bot.message用户发消息记忆模块、工作流模块
bot.responseBot生成回复记忆模块、插件模块
plugin.called插件被调用记忆模块、监控模块
workflow.started工作流启动Bot模块、监控模块
memory.stored记忆被存储监控模块

通过事件机制，新增一个插件不需要改Bot代码，只需要订阅它关心的事件。反过来，Bot代码重构，插件也完全不受影响。

4模块内部：为什么不用的功能别乱加

说完模块间通信，再说说模块内部。

我见过最糟糕的设计是：在一个函数里塞了20个参数，做了15件不同的事。这不是能力强，是缺乏边界意识。

每个模块应该有：

  • 明确的输入——这个函数需要什么？
  • 明确的输出——这个函数返回什么？
  • 明确的职责——这件事我只做，不做别的
python# 好的设计：一个类只做一件事
class BotConfig:
    # 只负责Bot配置的管理
    pass

class BotExecutor:
    # 只负责Bot的执行逻辑
    pass

class BotVersionManager:
    # 只负责Bot的版本控制
    pass

专业的人做专业的事，专业的类做专业的事。一个Bot类干所有事，那是学生作业；生产级代码，一个类只干一件事。

5实战：怎么画出模块边界图

很多人说"我知道要划分子模块，但不知道怎么画边界"。

我的经验是：先写代码，后画边界。不要想着一开始就把边界划清楚，这是不可能的。

正确流程是：

  1. 先写最核心的代码，让功能跑起来
  2. 观察哪些地方在频繁修改
  3. 把这些频繁修改的地方划成一个模块
  4. 定义好模块的接口（Interface）
  5. 后续修改只改模块内部，不影响其他模块

myAgent的模块边界不是我想出来的，是根据实际开发过程中的改动频率总结出来的。

💡 总结：模块边界清晰是架构设计的核心。模块间通信用事件驱动，模块内职责单一。不要过度设计，但也不要设计不足。最好的架构是改需求的时候只需要改一个地方。
