Bot执行引擎

数据模型是静态的，Prompt是配置，执行引擎才是动态的——一个请求进来，Bot是怎么处理的？

执行引擎是myAgent最核心的模块。它负责：接收请求、调用记忆、调用LLM、处理工具调用、返回响应。所有其他模块——插件、工作流、记忆——都围绕执行引擎协作。

💡 核心观点：执行引擎的核心是"编排"——不是自己干所有事，而是协调各个模块各司其职。好的执行引擎是"我在调度，不是在干活"。

1执行流程：请求到响应的旅程

一个用户消息到达Bot执行引擎，完整的处理流程是这样的：

Figure: Bot Execution Flow - From request to response

text# Bot执行流程
用户消息
    ↓
1. 会话管理：查找或创建会话
    ↓
2. 记忆召回：从记忆中获取相关上下文
    ↓
3. Prompt渲染：用变量和记忆组装完整Prompt
    ↓
4. LLM调用：发送到LLM获取响应
    ↓
5. 工具处理：如果需要工具调用，执行工具
    ↓
6. 记忆存储：把本次对话存入记忆
    ↓
7. 返回响应

这个流程看起来简单，但每一步都有坑。

2会话管理：找到属于你的上下文

第一步是会话管理。用户发起请求，系统要找到这个用户的会话上下文。

pythonclass SessionManager:

    def get_or_create_session(self, bot_id: str, user_id: str) -> Conversation:
        conv = db.query(Conversation).filter(
            Conversation.bot_id == bot_id,
            Conversation.user_id == user_id,
            Conversation.status == "active"
        ).first()

        if not conv:
            conv = Conversation(
                bot_id=bot_id,
                user_id=user_id,
                bot_version_id=self._get_bot_version_id(bot_id),
            )
            db.add(conv)

        return conv

会话管理的关键设计：一个用户对一个Bot只有一个活跃会话。这样简化了上下文管理的复杂度。

3消息历史：组装完整的对话上下文

拿到会话后，需要获取历史消息，组装成完整的对话上下文。

pythonasync def build_messages(self, conv: Conversation) -> List[Dict]:
    messages = []

    # 1. 系统Prompt
    bot = self.bot_service.get_bot(conv.bot_id)
    system_prompt = self._render_system_prompt(bot)
    messages.append({
        "role": "system",
        "content": system_prompt
    })

    # 2. 历史消息（限制条数，避免超出Token限制）
    history = self.message_repo.get_recent(
        conv.id,
        limit=self._get_max_history(bot.model)
    )
    messages.extend([{
        "role": m.role,
        "content": m.content
    } for m in history])

    return messages

历史消息不能无限制存储，因为LLM有Token上限。需要根据模型的最大上下文长度，动态计算能存多少条历史消息。

4限流控制：保护你的LLM调用

执行引擎必须有限流能力。不然用户刷接口，你的API配额分分钟用完。

pythonfrom redis import Redis

class RateLimiter:

    def __init__(self, redis_client: Redis):
        self.redis = redis_client

    async def check_rate_limit(self, user_id: str, bot_id: str) -> bool:
        key = f"rate_limit:{user_id}:{bot_id}"
        
        # 滑动窗口限流：每分钟最多N次
        count = await self.redis.get(key)
        if count and int(count) >= 60:
            return False  # 超限

        await self.redis.incr(key)
        await self.redis.expire(key, 60)  # 60秒窗口
        return True

限流是保护系统稳定性的最后一道防线。Redis的滑动窗口算法简单高效，能应对大多数限流场景。

💡 总结：Bot执行引擎负责完整的请求处理流程：会话管理→消息历史→Prompt渲染→LLM调用→工具处理→记忆存储→响应返回。执行引擎是编排者，不是执行者。限流保护系统不被冲垮。
