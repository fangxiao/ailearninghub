2熔断器：三态状态机

熔断器的思想来自电路里的"保险丝"：电流过载时自动断开，保护电器不被烧毁。在Agent里，当某个Skill连续失败到一定程度，就"断开"它，不再往这个坑里扔请求。

熔断器有三个状态，构成一个状态机：

图1：熔断器三态状态机

stateDiagram-v2 [*] --> CLOSED CLOSED --> OPEN: 失败数 >= 阈值
(failure_threshold) OPEN --> HALF_OPEN: 超过恢复时间
(recovery_timeout) HALF_OPEN --> CLOSED: 探测请求成功
record_success HALF_OPEN --> OPEN: 探测请求失败
record_failure note right of CLOSED: 正常放行所有请求\n成功/失败都计数 note right of OPEN: 拒绝所有请求\n直接走降级逻辑 note right of HALF_OPEN: 放行一个探测请求\n根据结果决定去留

三个状态各自的行为：

  • CLOSED（关闭态）：正常工作，所有请求都放行。每次失败就计数，失败数达到阈值就跳到OPEN。
  • OPEN（打开态）：熔断中，所有请求直接拒绝，根本不调Skill，立即走降级（fallback）。给故障Skill一个"喘息"的时间。
  • HALF_OPEN（半开态）：恢复时间到了，放行一个探测请求试探一下。成功了就回CLOSED（故障恢复），失败了就回OPEN（继续等）。

这里有个反直觉的设计：熔断器不是为了让系统"不失败"，而是为了让系统"快速失败"。OPEN状态下1毫秒就返回降级响应，比傻等30秒超时强一万倍。快速失败 = 快速恢复。

3CircuitBreaker实现代码

看实现。我们的熔断器是按Skill粒度隔离的——每个Skill有独立的状态机，一个Skill熔断不影响其他Skill：

Python

import time
import threading
from typing import Dict


class CircuitBreaker:
    """熔断器 - 保护Harness免受故障Skill的影响"""

    CLOSED = "closed"      # 正常放行
    OPEN = "open"          # 熔断中，拒绝请求
    HALF_OPEN = "half_open"  # 半开，放行探测请求

    def __init__(self, failure_threshold: int = 5,
                 recovery_timeout: float = 30.0):
        self.failure_threshold = failure_threshold  # 失败阈值
        self.recovery_timeout = recovery_timeout    # 恢复等待秒数
        self.states: Dict[str, Dict] = {}           # 每个Skill独立状态
        self._lock = threading.Lock()               # 线程安全

    def can_execute(self, skill_name: str) -> bool:
        """检查技能是否可以执行（请求前调用）"""
        with self._lock:
            if skill_name not in self.states:
                self.states[skill_name] = {
                    "state": self.CLOSED,
                    "failures": 0,
                    "last_failure_time": 0
                }
                return True

            state = self.states[skill_name]

            if state["state"] == self.OPEN:
                # OPEN态：看是否到了恢复时间
                if time.time() - state["last_failure_time"] > self.recovery_timeout:
                    state["state"] = self.HALF_OPEN  # 转半开，放行探测
                    return True
                return False  # 还没到时间，直接拒绝

            return True  # CLOSED / HALF_OPEN 都放行

    def record_success(self, skill_name: str):
        """记录成功 - HALF_OPEN回CLOSED，故障恢复"""
        with self._lock:
            if skill_name in self.states:
                self.states[skill_name]["state"] = self.CLOSED
                self.states[skill_name]["failures"] = 0

    def record_failure(self, skill_name: str):
        """记录失败 - 计数+1，达到阈值则转OPEN"""
        with self._lock:
            if skill_name not in self.states:
                self.states[skill_name] = {
                    "state": self.CLOSED,
                    "failures": 0,
                    "last_failure_time": 0
                }
            state = self.states[skill_name]
            state["failures"] += 1
            state["last_failure_time"] = time.time()
            if state["failures"] >= self.failure_threshold:
                state["state"] = self.OPEN  # 触发熔断

    def get_state(self, skill_name: str) -> str:
        """获取熔断器状态（给监控用）"""
        with self._lock:
            if skill_name not in self.states:
                return self.CLOSED
            return self.states[skill_name]["state"]

几个设计要点：

  • 按Skill隔离：states 是个字典，key是skill_name。订单Skill熔断了，FAQ Skill照样能用。
  • 线程安全：用了 threading.Lock，多个请求并发检查状态不会乱。
  • 三个方法的调用时机：请求前 can_execute，成功后 record_success，失败后 record_failure。
  • 参数可调：failure_threshold=5（连续5次失败熔断），recovery_timeout=30（30秒后试探恢复）。

4限流器：滑动窗口算法

熔断器管的是"故障Skill"，限流器管的是"过量请求"。无论请求来自恶意脚本还是真实大促，超过系统承载能力的请求一律挡在门外。

滑动窗口的核心思路：窗口不是固定的，而是随时间滑动。每次来请求，先清掉窗口外的过期请求，再看窗口内还剩多少。这样做的好处是不会像固定窗口那样在边界处出现"两倍流量"的漏洞。

注意一个细节：我们的限流是按user_id维度做的（key=user_id），不是全局限流。为什么？因为全局限流会害死老实用户——一个恶意用户把全局额度刷光，其他人全得背锅。按用户限流，坏人自己把自己限死，不影响别人。

5RateLimiter实现代码

Python

import time
import threading
from collections import defaultdict
from typing import Dict


class RateLimiter:
    """限流器 - 保护系统不被过量请求压垮"""

    def __init__(self, max_requests: int = 100, window_seconds: float = 60.0):
        self.max_requests = max_requests        # 窗口内最大请求数
        self.window_seconds = window_seconds    # 窗口大小（秒）
        self.requests: Dict[str, list] = defaultdict(list)  # 每用户一个时间戳列表
        self._lock = threading.Lock()

    def is_allowed(self, key: str = "default") -> bool:
        """检查是否允许请求（核心方法）"""
        with self._lock:
            now = time.time()
            window_start = now - self.window_seconds

            # 1. 清掉窗口外的过期时间戳（窗口滑动）
            self.requests[key] = [
                t for t in self.requests[key] if t > window_start
            ]

            # 2. 窗口内已满，拒绝
            if len(self.requests[key]) >= self.max_requests:
                return False

            # 3. 未满，记录这次请求的时间戳，放行
            self.requests[key].append(now)
            return True

    def get_wait_time(self, key: str = "default") -> float:
        """获取需要等待的秒数（给用户友好提示用）"""
        with self._lock:
            if key not in self.requests or not self.requests[key]:
                return 0.0
            now = time.time()
            oldest = self.requests[key][0]  # 最早的那个请求
            wait_time = (oldest + self.window_seconds) - now
            return max(0.0, wait_time)

    def get_stats(self, key: str = "default") -> Dict:
        """获取限流统计（给监控用）"""
        with self._lock:
            now = time.time()
            window_start = now - self.window_seconds
            active = [t for t in self.requests.get(key, []) if t > window_start]
            return {
                "current_rate": len(active),       # 当前窗口内请求数
                "max_rate": self.max_requests,     # 上限
                "window_seconds": self.window_seconds
            }

这个实现有两个贴心的小设计：

  • get_wait_time：被限流时不直接甩一句"请求太频繁"，而是告诉用户"请X秒后再试"。这个X就是最早那个请求过期的时间。
  • get_stats：暴露当前速率给监控，运维能实时看到哪个用户快到限额了。

6重试策略：指数退避

有些故障是瞬时的——网络抖一下、API偶发超时、服务重启中。这种时候直接放弃太可惜，重试一次可能就好了。但重试有讲究，不能无脑重试。

重试策略做法问题
立即重试失败后马上再调一次对方还在忙，大概率还是失败
固定间隔重试每次等1秒再重试对方恢复慢时浪费重试次数
固定次数重试重试3次，每次都立即调可能压垮正在恢复的服务
指数退避每次等待时间翻倍：1s→2s→4s✅ 给服务恢复时间，不雪上加霜

指数退避是工业界的事实标准。看实现：

Python

import time
import random


def retry_with_backoff(func, max_retries: int = 3,
                       base_delay: float = 1.0,
                       exceptions=(Exception,)):
    """指数退避重试 - 对瞬时故障自动重试
    
    Args:
        func: 要执行的函数
        max_retries: 最大重试次数
        base_delay: 基础等待秒数，每次翻倍
        exceptions: 哪些异常才重试
    """
    last_error = None
    for attempt in range(max_retries + 1):  # 1次正常 + N次重试
        try:
            return func()
        except exceptions as e:
            last_error = e
            if attempt == max_retries:
                break  # 重试次数用尽，抛出
            # 指数退避：1s → 2s → 4s → 8s...
            delay = base_delay * (2 ** attempt)
            # 加点抖动（jitter），避免多个客户端同步重试
            delay = delay + random.uniform(0, delay * 0.1)
            time.sleep(delay)
    raise last_error


# 用法：调用LLM时套一层重试
def call_llm_with_retry(prompt: str):
    return retry_with_backoff(
        lambda: llm.chat(prompt),
        max_retries=3,
        base_delay=1.0,
        exceptions=(TimeoutError, ConnectionError)  # 只重试瞬时故障
    )

两个关键点：
1. 只重试可重试的异常。超时、连接错误重试有意义；但"参数错误""鉴权失败"这种业务错误重试100次还是错。
2. 加抖动（jitter）。如果不加抖动，多个客户端在同一时刻重试，会形成"重试风暴"，反而把刚恢复的服务再次打挂。

8本篇总结：三重防护的3个核心思想

核心思想1：快速失败 > 缓慢成功
熔断器的OPEN态1毫秒返回降级，比傻等30秒超时强一万倍。失败时也能优雅退场，才是生产级Agent。

核心思想2：按维度隔离，避免连锁故障
熔断按Skill隔离，限流按user_id隔离。一个故障点不该拖垮整个系统，一个坏用户不该影响好用户。

核心思想3：重试要克制，退避要抖动
只重试瞬时故障，不重试业务错误；指数退避给服务恢复时间，加抖动避免重试风暴。

日志 Logs"刚才发生了什么？"离散的事件排障、审计、回放
链路追踪 Traces"为什么会这样？"因果的链路性能定位、根因分析

三层的关系是层层下钻的：仪表盘上看到"解决率掉了"（指标）→ 点进去看哪些对话没解决（日志）→ 再看其中一条的完整Skill调用链，定位到是哪个环节断了（链路追踪）。没有指标你不知道有问题，没有日志你找不到现场，没有链路你定位不到根因。

3MetricsCollector实现代码

我们先从第一层"指标"做起。MetricsCollector负责记录每次对话和每次Skill执行，并聚合成仪表盘数据：

Python

import json
import time
import os
from typing import Dict, List, Any


class MetricsCollector:
    """指标收集器 - 收集客服对话的各项指标"""

    def __init__(self, log_file: str = "data/metrics_log.json"):
        self.log_file = log_file
        self.logs: List[Dict] = []
        self._load()  # 启动时加载历史日志

    def _load(self):
        try:
            if os.path.exists(self.log_file):
                with open(self.log_file, 'r', encoding='utf-8') as f:
                    self.logs = json.load(f)
        except (json.JSONDecodeError, IOError):
            self.logs = []

    def _save(self):
        os.makedirs(os.path.dirname(self.log_file) or '.', exist_ok=True)
        with open(self.log_file, 'w', encoding='utf-8') as f:
            json.dump(self.logs, f, ensure_ascii=False, indent=2)

    def log_conversation(self, conversation: Dict):
        """记录一次对话（含业务结果）"""
        log_entry = {
            "timestamp": time.time(),
            "user_id": conversation.get("user_id", "anonymous"),
            "skill": conversation.get("skill", "unknown"),
            "intent": conversation.get("intent", "unknown"),
            "resolved": conversation.get("resolved", False),    # 是否解决
            "handoff": conversation.get("handoff", False),       # 是否转人工
            "response_time_ms": conversation.get("response_time_ms", 0),
            "tokens_used": conversation.get("tokens_used", 0),
            "success": conversation.get("success", True)
        }
        self.logs.append(log_entry)
        self._save()

    def log_skill_execution(self, skill_name: str, success: bool,
                            duration_ms: float, error: str = ""):
        """记录一次Skill执行（含性能数据）"""
        self.logs.append({
            "timestamp": time.time(),
            "type": "skill_execution",
            "skill": skill_name,
            "success": success,
            "duration_ms": duration_ms,
            "error": error
        })
        self._save()

    def get_dashboard(self) -> Dict[str, Any]:
        """聚合生成仪表盘数据"""
        conv_logs = [l for l in self.logs if "resolved" in l]
        skill_logs = [l for l in self.logs if l.get("type") == "skill_execution"]

        total = len(conv_logs)
        resolved = sum(1 for l in conv_logs if l.get("resolved"))
        handoffs = sum(1 for l in conv_logs if l.get("handoff"))
        response_times = [l.get("response_time_ms", 0)
                          for l in conv_logs
                          if l.get("response_time_ms", 0) > 0]

        # 按Skill聚合统计
        skill_stats: Dict[str, Dict] = {}
        for sl in skill_logs:
            name = sl.get("skill", "unknown")
            if name not in skill_stats:
                skill_stats[name] = {"total": 0, "success": 0, "total_time": 0}
            skill_stats[name]["total"] += 1
            if sl.get("success"):
                skill_stats[name]["success"] += 1
            skill_stats[name]["total_time"] += sl.get("duration_ms", 0)

        for name in skill_stats:
            s = skill_stats[name]
            s["avg_time_ms"] = round(s["total_time"] / s["total"], 1) if s["total"] > 0 else 0
            s["success_rate"] = round(s["success"] / s["total"], 3) if s["total"] > 0 else 0

        return {
            "total_conversations": total,
            "resolved_rate": round(resolved / total, 3) if total > 0 else 0,
            "handoff_rate": round(handoffs / total, 3) if total > 0 else 0,
            "avg_response_time_ms": round(sum(response_times) / len(response_times), 1) if response_times else 0,
            "skill_stats": skill_stats
        }

注意两个设计点：

  • 两类日志分开记：log_conversation 记业务结果（解决/转人工），log_skill_execution 记技术性能（耗时/成功/错误）。业务看前者，研发看后者。
  • 持久化到JSON：每次记录都 _save() 落盘，服务重启后 _load() 恢复，指标不丢。生产环境可换成时序数据库。

5告警机制：从"救火"到"防火"

指标是用来"看"的，告警是用来"叫"的。没有告警的指标，等于你装了仪表盘但从不抬头看。告警机制让系统在出问题时主动找你，而不是等用户投诉。

class AlertRule:
    """告警规则定义"""
    def __init__(self, name: str, metric: str,
                 threshold: float, operator: str = ">",
                 window_minutes: int = 5):
        self.name = name
        self.metric = metric          # 监控哪个指标
        self.threshold = threshold    # 阈值
        self.operator = operator      # > / < / ==
        self.window_minutes = window_minutes  # 统计窗口


class AlertManager:
    """告警管理器 - 指标越线就触发告警"""

    def __init__(self, metrics: MetricsCollector):
        self.metrics = metrics
        self.rules: list = []
        self.alert_history: list = []

    def add_rule(self, rule: AlertRule):
        self.rules.append(rule)

    def check(self) -> list:
        """检查所有规则，返回触发的告警"""
        dashboard = self.metrics.get_dashboard()
        triggered = []

        for rule in self.rules:
            value = dashboard.get(rule.metric, 0)
            is_breached = (
                (rule.operator == ">" and value > rule.threshold) or
                (rule.operator == "<" and value < rule.threshold)
            )
            if is_breached:
                alert = {
                    "rule": rule.name,
                    "metric": rule.metric,
                    "value": value,
                    "threshold": rule.threshold,
                    "time": time.time()
                }
                triggered.append(alert)
                self.alert_history.append(alert)
                # 这里可接入钉钉/飞书/邮件等通知通道

        return triggered


# 注册告警规则

A/B测试的核心实现就是按用户分流 + 分别统计 + 显著性检验：

Python

import hashlib


class ABTestRouter:
    """A/B测试分流器 - 按user_id稳定分流"""

    def __init__(self, experiment_name: str,
                 variants: list = ["A", "B"],
                 ratios: list = [50, 50]):
        self.experiment = experiment_name
        self.variants = variants
        self.ratios = ratios  # 流量比例

    def get_variant(self, user_id: str) -> str:
        """根据user_id稳定分流（同一用户每次进同一组）"""
        # 哈希后取模，保证分流稳定且均匀
        h = int(hashlib.md5(
            f"{self.experiment}:{user_id}".encode()
        ).hexdigest(), 16) % 100

        cumulative = 0
        for variant, ratio in zip(self.variants, self.ratios):
            cumulative += ratio
            if h < cumulative:
                return variant
        return self.variants[-1]


def compare_variants(metrics: MetricsCollector,
                     metric: str = "resolved_rate") -> dict:
    """对比A/B两组的指标差异"""
    # 分别过滤A组和B组的日志（日志里要记录实验分组）
    dashboard_a = metrics.get_dashboard()  # 实际应按variant过滤
    dashboard_b = metrics.get_dashboard()

    value_a = dashboard_a.get(metric, 0)
    value_b = dashboard_b.get(metric, 0)
    diff = value_b - value_a
    lift = diff / value_a if value_a > 0 else 0

    return {
        "metric": metric,
        "variant_a": value_a,
        "variant_b": value_b,
        "diff": round(diff, 3),
        "lift_pct": round(lift * 100, 1),  # 提升百分比
        "winner": "B" if value_b > value_a else "A"
    }

这里有个关键设计：用user_id哈希分流，而不是随机分流。为什么？因为同一个用户必须始终进同一组，否则他这次体验A、下次体验B，前后不一致会产生噪音数据。哈希分流保证"同一用户永远在同一组"，实验结果才干净。

A/B测试常见的一个坑：样本量不够就下结论。100条对话里A组解决率75%、B组80%，能说B更好吗？不能——这个差异可能是随机波动。正经做法是算统计显著性（p值<0.05才认），样本至少上千条。靠感觉调优，不如不调。

1为什么需要热插拔？一个真实的故障故事

去年双十一，我亲历了一次"血的教训"。那天下午2点，运营同学跑过来："直播间突然涌入3万用户，抢购活动要提前开！需要加一个秒杀咨询Skill，专门回答直播间的库存、发货、优惠问题。"

当时我们的做法是：

  1. 写好秒杀Skill的代码
  2. 合并到主分支
  3. 重启Harness服务
  4. 重新注册所有Skill
  5. ……整个过程花了7分钟

7分钟听起来不长？但在双十一高峰时段：
— 每分钟流失 8000+ 个潜在客户
— 竞争对手的客服Agent已经在接待这些用户
— 你的品牌形象在用户心里打了折扣

事后复盘发现，这7分钟的停服直接导致了320万GMV的损失。这不是技术问题，这是业务问题。

热插拔就是为了解决这个痛点。它的核心价值是：在不中断服务的前提下，动态加载、卸载、升级Skill。这意味着：

场景传统方式热插拔方式
紧急加功能停服部署（5-10分钟）动态加载（秒级）
修复线上Bug停服部署 + 回归测试灰度发布 + 快速回滚
A/B测试部署两套环境同一环境按流量切分
版本回退重新部署旧版本一键切回旧版本

灰度发布分三个阶段：

阶段一：小流量验证（5%）
选取5%的流量（可以按用户ID哈希、地区、渠道等维度）打到新版本。主要验证核心功能是否正常、关键指标是否达标。观察时间建议不少于30分钟。
阶段二：逐步扩量（20% → 50%）
小流量稳定后，逐步扩大比例。每个阶段至少观察15分钟，确保没有长尾问题。同时对比新旧版本的核心指标：成功率、响应时间、用户满意度。
阶段三：全量发布（100%）
全量切流后，继续密切监控至少2小时。确认稳定后，旧版本进入"待命"状态，保留回滚能力。24小时无问题后，旧版本可标记为"已归档"。

实战经验：我们在生产环境用了3天时间把灰度发布的自动化跑通。核心指标是Skill执行成功率和平均响应时间。新版本成功率低于旧版本超过2%，或响应时间上涨超过50ms，就自动触发回滚。上线半年来，灰度发布拦截了3次潜在故障。

4热插拔核心实现

现在来看核心代码。热插拔的实现思路是：用Python的importlib动态加载模块，用版本注册表管理多版本。

# skill_loader.py - 动态加载Skill模块
import importlib
import importlib.util
import sys
import os
import time
from typing import Dict, Optional, Type
from dataclasses import dataclass, field
from enum import Enum

class SkillStatus(Enum):
    REGISTERED = "registered"
    LOADING = "loading"
    READY = "ready"
    GRAYSCALE = "grayscale"
    FULL = "full"
    DISABLED = "disabled"
    FAILED = "failed"

@dataclass
class SkillVersion:
    version: str
    module_path: str
    status: SkillStatus = SkillStatus.REGISTERED
    traffic_percent: int = 0
    load_time: float = 0
    error_msg: str = ""

class HotReloadLoader:
    """Skill热插拔加载器"""

    def __init__(self):
        self._versions: Dict[str, Dict[str, SkillVersion]] = {}
        self._current: Dict[str, str] = {}
        self._modules: Dict[str, Type] = {}

    def load_skill(self, skill_name: str, module_path: str,
                   version: str) -> bool:
        """动态加载一个Skill"""
        key = f"{skill_name}@{version}"
        try:
            spec = importlib.util.spec_from_file_location(
                key, module_path
            )
            module = importlib.util.module_from_spec(spec)
            sys.modules[key] = module
            spec.loader.exec_module(module)

            self._versions.setdefault(
                skill_name, {}
            )[version] = SkillVersion(
                version=version,
                module_path=module_path,
                status=SkillStatus.READY,
                load_time=time.time()
            )
            self._modules[key] = module
            return True
        except Exception as e:
            if skill_name in self._versions:
                self._versions[skill_name].get(
                    version, SkillVersion(
                        version, module_path,
                        SkillStatus.FAILED, error_msg=str(e)
                    )
                )
            return False

    def switch_version(self, skill_name: str,
                       version: str) -> bool:
        """切换Skill版本"""
        versions = self._versions.get(skill_name, {})
        if version not in versions:
            return False
        self._current[skill_name] = version
        return True

    def set_traffic(self, skill_name: str,
                    version: str, percent: int):
        """设置灰度流量比例"""
        versions = self._versions.get(skill_name, {})
        if version in versions:
            v = versions[version]
            v.traffic_percent = percent
            v.status = (SkillStatus.GRAYSCALE
                       if percent < 100
                       else SkillStatus.FULL)

    def get_active_skill(self, skill_name: str,
                         user_id: str = "") -> Optional[Type]:
        """根据用户ID选择激活的Skill版本"""
        current = self._current.get(skill_name)
        if not current:
            return None

        versions = self._versions.get(skill_name, {})
        active_version = current

        for ver, info in versions.items():
            if info.status == SkillStatus.DISABLED:
                continue
            if ver == current:
                continue
            if info.status in (SkillStatus.GRAYSCALE,
                               SkillStatus.FULL):
                if self._should_route_to(user_id, info):
                    active_version = ver
                    break

        key = f"{skill_name}@{active_version}"
        module = self._modules.get(key)
        if module and hasattr(module, 'create_skill'):
            return module.create_skill()
        return None

    def _should_route_to(self, user_id: str,
                         info: SkillVersion) -> bool:
        """基于用户ID哈希决定是否路由到新版本"""
        if info.traffic_percent >= 100:
            return True
        if info.traffic_percent <= 0:
            return False
        hash_val = hash(user_id) % 100
        return hash_val < info.traffic_percent

来看关键方法解析：

方法作用核心逻辑
load_skill()动态加载Skill模块用importlib加载Python文件，支持任意版本
switch_version()切换当前版本修改版本指针，瞬间生效
set_traffic()设置灰度比例0-100整数，代表流量百分比
get_active_skill()获取当前Skill实例根据user_id哈希决定走哪个版本

5Harness集成：改造chat流程

热插拔加载器写好了，接下来要把它集成到Harness的核心流程里。改造的重点在路由决策和Skill获取环节：

# harness.py 改造后的chat流程
class HotReloadHarness:
    def __init__(self, config):
        self.loader = HotReloadLoader()
        self._init_skills(config)

    def _init_skills(self, config):
        for skill_cfg in config.skills:
            self.loader.load_skill(
                skill_cfg.name,
                skill_cfg.module_path,
                skill_cfg.version
            )

    def chat(self, user_input: str,
             user_id: str = "anonymous") -> str:
        # ... 前置Skill处理 ...

        # 路由决策
        skill_name = self.router.route(
            user_input, context
        )

        # 关键变化：通过loader获取Skill实例
        skill = self.loader.get_active_skill(
            skill_name, user_id
        )

        if not skill:
            skill = self.loader.get_active_skill(
                "general", user_id
            )

        # 执行Skill
        try:
            result = skill.execute(user_input, context)
        except Exception as e:
            result = skill.on_error(e, context)

        # ... 后续处理 ...
        return result.response

    # 运维接口：动态管理
    def deploy_skill(self, name: str, path: str,
                     version: str, grayscale: int = 5):
        """部署新版本Skill并开启灰度"""
        self.loader.load_skill(name, path, version)
        self.loader.set_traffic(name, version, grayscale)

    def rollback_skill(self, name: str):
        """一键回滚到上一个版本"""
        current = self.loader._current.get(name)
        versions = self.loader._versions.get(name, {})
        for ver in versions:
            if ver != current:
                self.loader.switch_version(name, ver)
                break

    def promote_skill(self, name: str, version: str):
        """将灰度版本提升为正式版本"""
        self.loader.set_traffic(name, version, 100)
        self.loader.switch_version(name, version)

改造后的Harness多了三个运维接口：

  • deploy_skill() — 部署新版本并开启灰度，一行代码完成
  • rollback_skill() — 一键回滚，从发现问题到切回旧版只需1秒
  • promote_skill() — 灰度通过后全量上线，流量瞬间切到新版本

6A/B测试与动态切流

热插拔的另一个高价值场景是A/B测试。比如你想测试两种促销话术哪种转化率更高，不需要部署两套环境，直接用同一个Skill的两个版本就行：

# A/B测试示例
def run_ab_test(self, skill_name: str,
                version_a: str, version_b: str,
                split_ratio: float = 0.5,
                duration_minutes: int = 60):
    """运行A/B测试"""
    self.loader.load_skill(skill_name, f"{skill_name}_a.py",
                           version_a)
    self.loader.load_skill(skill_name, f"{skill_name}_b.py",
                           version_b)

    self.loader.set_traffic(skill_name, version_a,
                            int(split_ratio * 100))
    self.loader.set_traffic(skill_name, version_b,
                            int((1 - split_ratio) * 100))

    self._start_ab_monitor(skill_name, version_a,
                           version_b, duration_minutes)

def _start_ab_monitor(self, skill_name, va, vb, duration):
    end_time = time.time() + duration * 60
    metrics = {va: [], vb: []}
    while time.time() < end_time:
        a_rate = self.metrics.get_success_rate(
            skill_name, va
        )
        b_rate = self.metrics.get_success_rate(
            skill_name, vb
        )
        metrics[va].append(a_rate)
        metrics[vb].append(b_rate)
        time.sleep(30)
    return self._analyze_ab_result(metrics)

A/B测试的好处是零成本切换。两个版本的Skill并行运行，按用户ID哈希分流，互不干扰。测试结束后，可以直接把胜出的版本设为正式版本。整个过程不需要重启服务，不需要额外部署资源。
