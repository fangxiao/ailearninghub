客服Agent进化论 ①

别再写if/else了！

我见过太多客服系统，每加一个业务场景就要改核心代码，改到最后没人敢动。单体插件架构是技术债的重灾区——插件耦合、路由硬编码、改一处动全身。于是我们彻底重构，引入 Harness 和 Skill 两层抽象。本篇带你从零搭建这套可插拔架构，告别if/else地狱。

💡 如果你看过之前的《客服Agent实战系列》，应该熟悉V1插件架构。本篇是加强版开篇，我们来聊聊怎么把那个原型升级成真正的生产级架构。

1V1的困境：为什么单体插件架构走不通？

先回忆一下V1版本的架构。在《客服Agent实战系列》里，我们用了一个"插件管道"模式：

图1：V1单体插件架构

表面上看插件化了，但实际写起来是这样的：

# V1 的路由代码 —— 一个巨大的 if/else
def route(self, user_input):
    intent = self.intent_plugin.detect(user_input)
    
    if intent == "faq_query":
        return self.knowledge_plugin.handle(user_input)
    elif intent == "order_query":
        return self.order_plugin.handle(user_input)
    elif intent == "complaint":
        return self.sentiment_plugin.handle(user_input)
    elif intent == "handoff":
        return self.ticket_plugin.handle(user_input)
    # ... 每加一个插件，这里就要改
    elif intent == "new_scenario":
        return self.new_plugin.handle(user_input)  # 必须改核心！
    else:
        return self.llm.chat(user_input)

V1的三大痛点：

痛点1：耦合严重 —— Bot核心直接import每个插件，插件之间互相依赖。改一个插件可能波及核心。

痛点2：路由硬编码 —— 每加一个业务场景就要改路由函数，违反开闭原则。10个插件还好，50个呢？

痛点3：无法动态加载 —— 插件写死在代码里，想临时禁用某个插件？注释掉。想热插拔？做不到。

这些痛点在Demo阶段不明显，但一旦业务扩展到电商、金融、教育等多行业场景，系统就变成了"意大利面条代码"——牵一发而动全身。

2Harness+Skill：一套为客服Agent量身定做的架构

我们重新设计了架构，核心理念来自一个比喻：

组件比喻职责
HarnessCEO统一编排、调度、监控，对外唯一入口
Skill专业员工各司其职，FAQ、订单、投诉、问候……
Registry人力资源部管理所有Skill的注册、查找、生命周期
Router调度中心根据上下文把请求分发给最合适的Skill
CircuitBreaker保险丝某个Skill连续失败时自动熔断，防止雪崩

关键区别在于：Harness不关心具体业务。它不知道FAQ是什么，也不关心订单怎么查。Harness只做三件事：
1. 从Registry找到所有可用的Skill
2. 让Router决定用哪个Skill
3. 执行Skill，记录结果，处理异常

这意味着：加一个新业务场景 = 写一个新Skill + 注册，核心代码一行不用改。

3新旧架构对比：用数据说话

维度V1 单体插件V2 Harness+Skill

看到没？V2架构用更少的代码，做了更多的事。核心原因就是职责分离：Harness只管编排，Skill只管业务。

6Harness核心代码：一次chat的完整旅程

来看 harness.py 中 chat() 方法的核心逻辑。这是整个架构的心脏：

def chat(self, user_input: str, user_id: str = "anonymous") -> str:
    start_time = time.time()
    self.current_user_id = user_id
    
    # 1. 记录用户消息
    self.dialog.add_message("user", user_input)
    
    # 2. 限流检查
    if not self.limiter.is_allowed(user_id):
        return f"您的请求过于频繁，请稍后再试。"
    
    # 3. 构建上下文
    context = self._build_context(user_input)
    
    # 4. 执行前置Skill（情感分析等）
    pre_skills = self.registry.get_pre_skills()
    for pre_skill in pre_skills:
        result = pre_skill.execute(user_input, context)
        if result.need_handoff:
            return result.response
        context["sentiment"] = result.data.get("sentiment")
    
    # 5. 意图识别
    intent_skill = self.registry.get_skill("intent_recognition")
    intent_result = intent_skill.execute(user_input, context)
    context["intent"] = intent_result.data.get("intent")
    
    # 6. 路由决策
    skill = self.router.route(user_input, context,
                              self.registry.get_all_skills())
    
    # 7. 熔断检查
    if not self.breaker.can_execute(skill.name):
        skill = self.registry.get_skill("general")
    
    # 8. 执行Skill
    result = skill.execute(user_input, context)
    
    # 9. 记录结果
    self.breaker.record_success(skill.name)
    self.dialog.add_message("assistant", result.response)
    self.memory.record_interaction(user_id, ...)
    
    return result.response

9个步骤，清晰可追踪。每一步的职责都很明确，没有任何if/else判断具体业务。

注意了吗？Harness的代码里没有任何业务逻辑。它不知道FAQ是什么，不理解订单查询，甚至不处理"你好"。它只做编排——把请求交给合适的Skill，然后把结果返回。

这就是架构的力量：简单的核心 + 可扩展的Skill。

7Skill是怎么注册和发现的？

你可能会问：Harness怎么知道有哪些Skill？Router怎么决定用哪个？

答案是 SkillRegistry（注册中心）和 SkillRouter（路由器）的配合：

# harness.py 中的注册过程
def _register_skills(self):
    self.registry.register(SentimentSkill(self.config))
    self.registry.register(IntentRecognitionSkill(self.config))
    self.registry.register(GreetingSkill(self.config, self.memory))
    self.registry.register(FAQSkill(self.config, self.llm))
    self.registry.register(OrderSkill(self.config))
    self.registry.register(ComplaintSkill(self.config))
    self.registry.register(HandoffSkill(self.config))
    self.registry.register(MemorySkill(self.config, self.memory))
    self.registry.register(SlotFillingSkill(self.config, self.dialog))
    self.registry.register(ToolUseSkill(self.config, self.llm))
    self.registry.register(GeneralSkill(self.config, self.llm))

注册之后，Router通过两种方式选择Skill：

路由策略实现方式适用场景
意图映射intent→skill的硬映射规则意图明确的场景，如faq_query→faq
打分机制每个Skill的can_handle()返回0~1分意图不明确时的兜底策略
兜底Skillgeneral作为最后防线所有Skill都不匹配时
# skill_router.py 的核心路由逻辑
def route(self, user_input, context, skills):
    # 策略1：意图映射
    explicit_intent = context.get("intent")
    if explicit_intent in self._intent_rules:
        target = self._intent_rules[explicit_intent]
        for skill in skills:
            if skill.name == target:
                return skill
    
    # 策略2：打分选择
    best_skill, best_score = None, 0.0
    for skill in skills:
        score = skill.can_handle(user_input, context)
        if score > best_score:
            best_score = score
            best_skill = skill
    
    if best_score > 0.3:
        return best_skill
    
    # 策略3：兜底
    return self._skills.get(self._fallback)

三种策略层层递进，既保证了确定性，又提供了灵活性。

8本篇总结：架构设计的3个核心思想

核心思想1：关注点分离
Harness只管编排，Skill只管业务。核心代码不需要了解任何业务细节。

核心思想2：可插拔
新增Skill = 写代码 + register()。不需要改任何已有代码。

核心思想3：防御性设计
CircuitBreaker、RateLimiter、兜底Skill——层层保护，确保系统不会因为单个Skill故障而崩溃。
