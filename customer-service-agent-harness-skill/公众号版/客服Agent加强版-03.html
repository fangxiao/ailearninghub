客服Agent进化论 ③

Registry+Router：Skill的生存哲学

我见过太多同学写了五六个Skill，每个都实现了BaseSkill接口，有完整的can_handle和execute，自我感觉良好。然后跑起来一看——一个都没被调用。为什么？因为它们散落在代码各处，没人知道它们的存在，更没人知道该把请求派给谁。没有注册中心的Skill系统，就像没有通讯录的手机——你知道有人，但找不到；就像没有招聘的公司——你有十个HR，但没有候选人简历，面试个屁。

解决这个问题只需要两个东西：SkillRegistry（注册中心）和 SkillRouter（路由器）。前者管"你是谁、你能干什么"，后者管"来了个活，派给谁干"。看似简单，但这俩家伙才是整个Skill体系的灵魂——没有它们，Skill就是死的；有了它们，Skill才真正"活"起来。

我要说一句可能得罪人的话：真正的解耦，不是让Skill不知道彼此，而是让Skill不需要知道彼此。你以为Skill之间要互相通信？要知道对方是谁、有什么能力？错！只要有Registry和Router在中间调度，每个Skill只要做好自己的事，报好自己的家门，剩下的交给"组织"就行。这才是真正的解耦——不是隔绝，而是通过中间层实现的松耦合。

💡 如果你看过之前的《客服Agent实战系列》，应该熟悉V1的插件架构。本篇是加强版的第三篇，我们来聊聊 Skill 体系中最核心的两个组件——注册中心和路由器。

1SkillRegistry：Skill的"人事部"

SkillRegistry 是所有 Skill 的"人事档案管理中心"。每个 Skill 上线第一件事就是到 Registry 里"报到"——登记姓名、能力、触发词、优先级。Registry 把这些信息统一保管，需要的时候随时查。

它的核心操作就三个，跟人事管理一模一样：

操作方法类比说明
注册register(skill)新员工入职登记把Skill加入字典，记录name→skill的映射
查找get_skill(name)按姓名查工号按名称精确查找一个Skill
注销unregister(name)员工离职注销从字典移除，同时清理pre_skills列表
Python
# SkillRegistry核心实现（精简版）
class SkillRegistry:
    def __init__(self):
        self._skills = {}          # name → skill 的映射
        self._pre_skills = []      # 前置Skill列表

    def register(self, skill: BaseSkill):
        self._skills[skill.name] = skill
        if skill.pre_skill:
            self._pre_skills.append(skill)

    def unregister(self, name: str):
        if name in self._skills:
            skill = self._skills.pop(name)
            if skill.pre_skill and skill in self._pre_skills:
                self._pre_skills.remove(skill)

    def get_skill(self, name):
        return self._skills.get(name)

    def find_by_intent(self, intent):
        for skill in self._skills.values():
            if intent in skill.triggers:
                return skill
        return None

设计亮点：Registry 用一个字典搞定全部存储，查找 O(1)，注册和注销都是 O(1)。更妙的是它支持 pre_skill 概念——某些Skill（比如情感分析、意图识别）需要在主流程前先执行，Registry 会单独维护它们的列表，方便调度器在合适的时机调用。

2SkillRouter：请求的"调度中枢"

如果说 Registry 是"人事部"，那 Router 就是"调度室"。它的任务很明确：用户说了一句话，从注册的所有Skill里挑一个最合适的来处理。

Router 的路由决策分为三个层次，从"最精确"到"最宽松"，层层递进：

策略触发条件路由方式示例
精确匹配上下文有明确 intent按 intent→skill_name 映射表查找context.intent="order_query" → OrderSkill
模糊匹配无明确 intent 或映射未命中遍历所有Skill，调用 can_handle 打分"我的快递到哪了" → OrderSkill(0.9分)
兜底策略所有Skill打分都 < 0.3使用预设的 fallback_skill未识别 → GeneralSkill(闲聊)
Python
# SkillRouter核心路由逻辑
class SkillRouter:
    def route(self, user_input, context, skills):
        # 策略1：精确匹配（意图→Skill映射）
        explicit_intent = context.get("intent")
        if explicit_intent and explicit_intent in self._intent_rules:
            target = self._intent_rules[explicit_intent]
            for skill in skills:
                if skill.name == target:
                    return skill

        # 策略2：模糊匹配（can_handle打分最高者）
        best_skill, best_score = None, 0.0
        for skill in skills:
            if skill.pre_skill:
                continue
            score = skill.can_handle(user_input, context)
            if score > best_score:
                best_score = score
                best_skill = skill

        if best_skill and best_score > 0.3:
            return best_skill

        # 策略3：兜底策略
        if self._fallback_skill:
            for skill in skills:
                if skill.name == self._fallback_skill:
                    return skill

        return None

注意那个 0.3 的阈值——这是路由的"质量底线"。低于0.3分的匹配宁可不用，交给兜底Skill处理，也比让一个"半吊子"Skill硬上强。宁缺毋滥，是路由的基本素养。

3路由决策流程图

下面这张图完整展示了 Router 的决策过程——从接收用户输入到最终选定 Skill 的全部路径：

图1：SkillRouter 路由决策流程

整个流程的设计哲学是：先精确、再模糊、最后兜底。每一步都比上一步"宽松"，但也比上一步"不靠谱"。就像找人办事——先找指定的人，找不到再找最相关的，实在不行找个万能的。

4三个场景的路由实战

光说不练假把式。来看三个真实场景下，Router 是怎么决策的：

场景一：用户说"我要修改收货地址"
路由路径：
① 意图识别模块先输出 intent = "modify_address"
② Router 检查映射表："modify_address" → OrderSkill
③ 精确匹配命中，直接路由到 OrderSkill
④ OrderSkill.execute() 执行地址修改流程

命中策略：精确匹配
场景二：用户说"我的快递到哪了？"
路由路径：
① 意图识别无法明确识别（用户没说"订单"也没说"物流"）
② Router 跳过精确匹配，进入模糊匹配
③ 遍历所有Skill的 can_handle：
  - GreetingSkill: 0.05
  - OrderSkill: 0.9（"快递"命中触发词，"到哪"也相关）
  - FAQSkill: 0.2
④ OrderSkill 得分最高，且 > 0.3，命中

命中策略：模糊匹配
场景三：用户说"今晚上吃什么好呢？"
路由路径：
① 上下文无明确 intent
② 模糊匹配打分：
  - 所有Skill得分均 < 0.3（这是闲聊，不在业务范围内）
③ 最高分未达阈值，触发兜底策略
④ Router 返回 FallbackSkill（通常是 GeneralSkill 或转人工）
⑤ GeneralSkill 以闲聊方式回应，或礼貌转人工

命中策略：兜底策略

5Registry + Router 的协作全景

Registry 和 Router 是怎么配合的？一句话总结：Registry 提供"候选池"，Router 做"选择决策"。

图2：Registry 与 Router 协作关系

整个流程可以概括为四步：

  1. 启动时：所有Skill向Registry注册自己
  2. 请求到来：Router从Registry获取Skill列表作为候选
  3. 决策时：Router按三策略（精确→模糊→兜底）选出最佳Skill
  4. 执行时：由Harness调度选出的Skill执行execute()

一个容易被忽略的细节：Router 不需要知道 Registry 的存在——它接收的是一个 skills 列表，由外部（Harness）传进来。这意味着你可以轻松替换 Router 实现（比如换成基于机器学习的路由），而完全不需要动 Registry 或任何 Skill。依赖倒置，才是真正的可扩展。

6本篇总结

核心要点：

1. SkillRegistry 是"人事部"：register / get / unregister 三个核心操作，O(1) 时间复杂度

2. SkillRouter 是"调度室"：三策略路由——精确匹配 → 模糊匹配 → 兜底策略

3. 0.3 阈值是"质量底线"：宁缺毋滥，避免半吊子Skill硬上

4. 依赖倒置是关键：Router 不依赖 Registry，通过参数注入实现解耦

5. 协作模式：Registry 供人，Router 选人——各司其职，互不干涉

━━━ 接下来：别再堆Skill了！Harness编排才是核心 ━━━

01编排的分层模型

什么是编排？简单说就是：用户消息进来后，先让哪些Skill做预处理，再让哪个Skill做主处理，最后要不要做收尾工作。

Harness的编排模型把Skill分成了三个层级：

图1：Skill编排分层模型

层级 职责 典型Skill 执行时机
pre_skill 前置处理、信息注入 情感Skill、意图Skill 主路由之前
main_skill 核心业务逻辑 订单Skill、FAQ Skill、ToolUseSkill 主路由选中后
post_skill 后置处理、状态记录 记忆Skill、指标Skill 主处理完成后

核心设计思想：pre_skill负责"看路"——识别情感、判断意图，给main_skill铺路；main_skill负责"走路"——执行核心业务逻辑；post_skill负责"记账"——记录对话、更新指标。三层各司其职，互不干扰。

02pre_skill → main_skill → post_skill 三阶段

下面详细拆解每个阶段的职责和执行逻辑。

第一阶段：pre_skill 前置处理

pre_skill的特点是在主路由之前执行，而且可以有多个。它们的作用是给context注入关键信息，或者在特殊情况下直接拦截请求。

Python
pre_skills = self.registry.get_pre_skills()
for pre_skill in pre_skills:
    result = pre_skill.execute(user_input, context)
    if result.need_handoff:
        return result.response
    if result.data.get("sentiment_processed"):
        context["sentiment"] = result.data.get("sentiment")

每个pre_skill的处理结果有两种走向：

  • need_handoff=True：比如情感Skill检测到用户暴怒，直接转人工，流程终止
  • 注入context：比如意图Skill把识别出的意图写入context，供后续路由使用
为什么pre_skill要串行执行？
假设你有情感Skill和意图Skill两个pre_skill。情感Skill先跑，检测到用户是Level 2（不满），把情感信息写入context。然后意图Skill跑，它可以读取context中的情感信息，调整意图识别的策略（比如对愤怒用户更倾向于路由到投诉Skill）。

串行执行让pre_skill之间可以通过context传递信息，实现协同。

第二阶段：main_skill 主处理

pre_skill执行完后，Harness根据context中的信息（意图、情感等）通过路由器选择一个main_skill执行：

Python
skill = self.router.route(user_input, context, skills)

if not skill:
    skill = self.registry.get_skill("general")

if not self.breaker.can_execute(skill_name):
    skill = self.registry.get_skill("general")

result = skill.execute(user_input, context)

main_skill的选择经过三层把关：

  1. 路由器选择：根据意图匹配 + can_handle置信度，选最合适的Skill
  2. 兜底Skill：如果路由器选不出来，用general Skill兜底
  3. 熔断保护：如果首选Skill的熔断器已触发（连续失败太多次），切换到兜底Skill

第三阶段：post_skill 后置处理

main_skill执行完后，Harness进行收尾工作——记录对话、更新指标、写入记忆：

Python
self.dialog.add_message("assistant", response)
self.memory.record_interaction(
    user_id, intent, user_input, response
)
self._record(user_input, response, skill, start_time,
             resolved=resolved, handoff=handoff,
             intent=context.get("intent", "unknown"))

post_skill的职责通常由Harness内部的模块承担（DialogManager、UserMemory、MetricsCollector），而不是独立的Skill类。这样做的好处是：核心业务Skill不需要关心日志、监控这些横切关注点。

03chat()方法完整执行时序

下面用一个完整的时序图展示chat()方法从接收用户消息到返回回复的全过程：

图2：chat()方法完整执行时序图

这个时序图揭示了几个关键的设计点：

  • pre_skill可以短路整个流程：如果情感Skill检测到用户暴怒，直接转人工，后面的路由和main_skill都不会执行
  • 路由在pre_skill之后：路由器能拿到pre_skill注入的context信息（意图、情感），做出更精准的路由决策
  • 熔断保护在main_skill之前：如果某个Skill连续失败，熔断器会在调用前就切换，不让错误继续放大
  • post_skill由Harness承担：对话记录、指标收集、用户记忆这些横切关注点，由Harness统一处理

04编排实战：查订单 + 改地址

光说不练假把式。我们用一个复杂场景来演示编排的威力：

用户说："你好，我叫张三，我的订单20240601001能帮我查一下到哪了吗？另外，我想把收货地址改成北京市朝阳区建国路1号。"

这个请求包含了：查订单 + 改地址，两个业务意图。传统路由能处理吗？能，但很别扭。用编排的思路呢？让我们看看。

图3：编排实战流程

我们来一步步拆解这个过程中编排是怎么工作的：

步骤1：pre_skill阶段

情感Skill先执行，检测到用户是Level 0（中性），放行。然后意图Skill执行，识别出两个意图：order_query 和 modify_address。

Bash
# pre_skill执行
context = {"user_id": "user_001"}
context["sentiment"] = "Level 0"     # 情感Skill注入
context["intent"] = "order_query"     # 意图Skill注入（主意图）
context["intents"] = ["order_query", "modify_address"]  # 多意图

# 路由决策
skill = router.route(user_input, context, skills)
# 因为是多意图，传统Skill处理不了，
# 路由器选择了ToolUseSkill（因为can_handle返回0.6）

步骤2：main_skill阶段

路由器选择了ToolUseSkill（因为它支持多工具组合调用）。ToolUseSkill把query_order和modify_address两个工具暴露给LLM，LLM自主决定调用顺序和参数：

Bash
# ToolUseSkill执行
llm_result = llm.chat(
    messages=[{"role": "user", "content": "..."}],
    tools=[query_order, modify_address, ...]
)

# LLM决定：
# 先查订单，再改地址
# tool_calls = [
#   {"name": "query_order", "args": {"order_id": "20240601001"}},
#   {"name": "modify_address", "args": {"order_id": "20240601001", "address": "北京市朝阳区..."}}
# ]

LLM连续调用了两个工具：先查询订单状态，再修改收货地址。两个工具的结果都返回给LLM后，它生成了最终回复："您的订单20240601001目前正在配送中...收货地址已成功修改为北京市朝阳区建国路1号。"

步骤3：post_skill阶段

对话结束后，Harness自动完成了以下后置工作：

Bash
# post_skill（由Harness内部完成）
dialog.add_message("user", "查订单+改地址请求")
dialog.add_message("assistant", "订单配送中+地址已修改")
memory.record_interaction("user_001", "order_query", 
                          "用户请求", "LLM回复")
metrics.log_conversation({
    "skill": "tool_use",
    "resolved": True,
    "response_time_ms": 1250
})

05为什么编排比Skill本身更重要？

讲完实战，我们回到最开始的问题：为什么编排比Skill本身更重要？

反例：没有编排的Skill堆
• 情感Skill：独立运行，但没人把情感信息传递给订单Skill
• 订单Skill：能查订单，但不能和地址修改联动
• FAQ Skill：能回答问题，但不知道用户之前已经问过什么
• 结果：每个Skill都是孤岛，用户体验割裂
正例：有编排的Skill体系
• pre_skill把情感、意图注入context → 所有Skill都能感知
• main_skill由路由器智能选择 → 复杂场景由ToolUseSkill兜底
• post_skill统一记录 → 对话历史、用户画像持续积累
• 结果：Skill协同工作，用户体验流畅

我见过很多客服Agent项目，Skill写了20多个，但用户体验还是差。问题出在哪？不是Skill写得不好，而是没有编排。每个Skill都是"局部最优"，但没有一个"全局最优"的编排层来协调它们。

Harness就是这个编排层。它不解决具体业务问题，它解决的是"谁来解决问题"、"按什么顺序解决问题"的问题。

06编排的核心代码

最后看一下Harness.chat()方法的完整代码，理解编排是怎么落地的：

Python
def chat(self, user_input, user_id="anonymous"):
    # 1. 限流检查
    if not self.limiter.is_allowed(user_id):
        return "请求过于频繁，请稍后再试"

    # 2. 构建context
    context = self._build_context(user_input)

    # 3. pre_skill：前置处理
    for pre_skill in self.registry.get_pre_skills():
        result = pre_skill.execute(user_input, context)
        if result.need_handoff:
            return result.response
        context.update(result.data)

    # 4. 路由决策
    skill = self.router.route(user_input, context, ...)

    # 5. 熔断保护
    if not self.breaker.can_execute(skill.name):
        skill = self.registry.get_skill("general")

    # 6. main_skill执行
    result = skill.execute(user_input, context)

    # 7. post_skill：后置处理
    self.dialog.add_message("assistant", result.response)
    self.memory.record_interaction(user_id, ...)
    self._record(result)

    return result.response

去掉所有细节后，编排的骨架就是7步：限流 → 构建context → pre_skill → 路由 → 熔断 → main_skill → post_skill。

每一步都有它的职责，每一步都不可替代：

步骤 职责 不可替代性
限流 保护系统不被刷爆 没了它，系统会被恶意请求拖垮
构建context 准备上下文信息 没了它，Skill看不到用户历史
pre_skill 前置拦截和信息注入 没了它，愤怒用户直接进main_skill
路由 选择最合适的Skill 没了它，不知道该找谁处理
熔断 故障隔离 没了它，一个Skill挂掉影响所有
main_skill 核心业务处理 没了它，没有实际回复
post_skill 状态记录和监控 没了它，无法追溯和优化

总结一下：Skill是"兵"，Harness是"将"。兵再强，没有好将指挥，也是一盘散沙。

编排的本质是建立一套执行秩序——先做什么、后做什么、谁来做、做坏了怎么办。这套秩序让你的客服Agent从"一堆Skill"进化为"一个智能体"。

记住：别再堆Skill了，多花点时间在编排上。好的编排，比多写10个Skill更有价值。
