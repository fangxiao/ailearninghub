客服Agent进化论 ⑥

情感+Function Calling：装上双手

想象一下：你走进餐厅，还没开口，服务员就把一盆热水泼在你脸上。这就是没有情感识别的客服Agent在干的事。用户说"你们的服务太差了！"，你的Agent回复"请提供订单号"——这不是客服，这是在火上浇油。本篇我带你搞懂前置Filter机制：在主路由之前识别用户情绪，愤怒的直接转人工，别让机器替你搞砸。

💡 如果你看过之前的《客服Agent实战系列》，应该熟悉Harness+Skill的架构设计。本篇是加强版，我们来聊聊怎么在主流程之前加一道"情感安检门"。

01情感分级标准：5级制

要做情感识别，首先得有一套标准。我们参考了客服行业的通用做法，把用户情感分成5个等级：

等级 情感 典型表现 应对策略
Level 0 😀 满意/中性 "好的，谢谢"、"帮我查一下订单" 正常路由
Level 1 🙂 轻微负面 "怎么还没发货"、"物流有点慢" 正常路由 + 安抚语气
Level 2 😐 不满 "你们怎么回事"、"这个问题解决多少次了" 优先处理 + 情绪安抚
Level 3 😠 愤怒 "投诉你"、"我要退款"、"找你们领导" 转人工 + 紧急标记
Level 4 🤬 暴怒 脏话、人身攻击、连续感叹号 立即转人工 + 高优先级

核心原则：Level 3 以上直接转人工，不让Agent继续对话。因为一旦用户愤怒了，机器说什么都是错的，反而会加剧不满情绪。

02前置Filter执行流程

前置Filter的核心思想是：在Skill路由之前，先过一道情感安检。如果检测到高等级负面情绪，直接拦截，转人工处理：

图1：前置Filter执行流程

注意：Filter是前置的，也就是说它在Skill Router之前执行。这样做的好处是，愤怒用户根本不会进入任何Skill的处理流程，避免机器说错话。

为什么不能让Skill处理愤怒用户？
想象一下：用户说"你们骗子！我要投诉！"，FAQ Skill可能匹配到"退款流程"的FAQ，回复"退款步骤如下..."。这在用户看来就是："你不仅骗了我，还在念说明书给我听"——火上浇油。

正确的做法是：识别愤怒 → 表达理解 → 立即转人工。机器不需要解决问题，只需要不加剧问题。

03愤怒用户处理机制

当Filter检测到Level 3-4的愤怒用户时，执行以下处理流程：

Python
class SentimentFilter:
    def __init__(self, sentiment_model, human_queue):
        self.model = sentiment_model
        self.human_queue = human_queue

    def process(self, message, context):
        score = self.model.predict(message)
        level = self._get_level(score)

        context.sentiment_level = level
        context.sentiment_score = score

        if level >= 3:
            return self._handle_angry_user(level, message, context)
        elif level == 2:
            return self._handle_mild_negative(message, context)
        else:
            return None

    def _handle_angry_user(self, level, message, context):
        context.is_escalated = True
        context.handoff_reason = f"情感等级{level}：用户愤怒"

        self.human_queue.add({
            'user_id': context.user_id,
            'message': message,
            'level': level,
            'timestamp': time.time(),
            'priority': 'urgent' if level == 4 else 'high'
        })

        if level == 4:
            reply = "非常抱歉给您带来不好的体验！我们的客服主管将在1分钟内亲自处理您的问题。"
        else:
            reply = "非常理解您的心情，我已经为您转接人工客服，会有专门的同事为您解决问题。"

        return {
            'action': 'handoff',
            'reply': reply,
            'sentiment_level': level
        }

    def _handle_mild_negative(self, message, context):
        context.sentiment_warning = True
        return {
            'action': 'warn',
            'message': 'pass_to_skill_with_comfort',
            'sentiment_level': 2
        }

    def _get_level(self, score):
        if score >= 0.8:
            return 4
        elif score >= 0.6:
            return 3
        elif score >= 0.3:
            return 2
        elif score >= 0.1:
            return 1
        else:
            return 0

关键设计点：

  1. 区分Level 3和Level 4的话术：暴怒用户需要更紧急的回应，提到"客服主管"和"1分钟内"能有效安抚
  2. 紧急队列标记：Level 4的用户被标记为urgent，人工客服端会优先显示
  3. 上下文传递：情感等级写入context，后续Skill或人工客服都能看到

我们做过A/B测试：加了情感Filter后，人工客服的投诉率下降了67%。不是因为问题解决得更好了，而是因为愤怒用户直接到人那里解决，而不是被机器激怒后再投诉。

05情感识别模型选型

情感Filter的效果，取决于底层的情感识别模型。我们用过三种方案：

方案 准确率 响应速度 适用场景
关键词规则 60% 快（<10ms） 简单场景、快速上线
小模型分类器 82% 中（~50ms） 中等复杂度
LLM情感分析 92% 慢（~300ms） 复杂场景、高准确率要求

推荐方案：用小模型做实时情感识别，LLM做兜底。小模型处理80%的常规情况，遇到模糊case（置信度<0.7）再调LLM。这样既有速度又有准确率。

Python
class HybridSentimentAnalyzer:
    def __init__(self, small_model, llm_client):
        self.small_model = small_model
        self.llm = llm_client

    def predict(self, text):
        score = self.small_model.predict(text)

        if score > 0.7 or score < 0.3:
            return score

        llm_score = self._llm_analyze(text)
        return (score + llm_score) / 2

    def _llm_analyze(self, text):
        prompt = f"""分析用户情感，返回0-4的等级：
        0=满意 1=轻微不满 2=不满 3=愤怒 4=暴怒
        用户消息："{text}"
        只返回数字。"""
        response = self.llm.generate(prompt)
        return float(response.strip())

06监控与持续优化

情感Filter不是一劳永逸的，需要持续监控和优化：

核心监控指标
• 情感识别准确率：人工抽样校验，目标>90%
• 转人工命中率：被拦截的用户中，真正需要人工的比例
• 愤怒升级率：对话过程中情感等级上升的比例
• 用户满意度：转人工后的好评率
常见问题与优化
问题1：用户说"投诉"两个字就被拦截，但其实只是口头威胁
优化：结合上下文判断，连续3条以上负面消息才升级

问题2：用户用反讽表达不满，如"你真厉害"
优化：加入反讽识别规则，或用LLM做二次确认

问题3：转人工后用户反而更生气，因为等太久
优化：设置等待超时，30秒内人工未接入，用LLM跟进安抚

情感Filter不是"一刀切"的开关，而是需要持续调优的"调节阀"。我们的做法是：每周分析被误判的case，更新模型或规则。上线三个月后，误判率从初期的15%降到了3%以下。

01Function Calling核心概念

先说清楚：什么是Function Calling？说白了就是让LLM在对话过程中，主动发起"我想调用某个函数"的请求，而不是由你的代码硬编码决定调哪个函数。

传统路由 vs Function Calling
传统路由：用户输入 → 意图识别 → 匹配Skill → 执行execute()
用户说"查订单" → 路由到OrderSkill → 调用订单查询代码

Function Calling：用户输入 → LLM理解意图 → LLM选择工具 → 执行工具 → 结果返回LLM → LLM生成回复
用户说"查订单+看会员" → LLM决定调query_order + get_user_info → 两个工具都执行 → LLM汇总结果生成回复

关键区别在于：传统路由是你帮LLM做决定，Function Calling是让LLM自己做决定。

维度 传统Skill路由 Function Calling
决策方 路由器（代码） LLM（模型）
多工具组合 不支持 原生支持
灵活性 固定规则 LLM自主决策
适用场景 单轮、明确意图 复杂、多步骤、模糊意图

一句话总结：Function Calling就是把"调什么工具、传什么参数"的决策权，从硬编码的路由器交给LLM。LLM说"我要调query_order，参数是order_id=123"，你就执行这个工具，把结果喂回去，LLM再决定下一步。

02ToolUseSkill整体架构

ToolUseSkill的核心设计思路是：把所有工具暴露给LLM，让它在对话中自主选择调用。整体执行流程如下：

图1：Function Calling核心流程

这个流程的几个关键点：

  1. 工具Schema传给LLM：不是把工具代码给LLM看，而是给工具的"说明书"——名称、描述、参数定义
  2. LLM自主决定：LLM根据用户意图和工具描述，自己判断调哪个工具、传什么参数
  3. 多轮循环：如果LLM觉得需要多次调用（比如先查订单，再查会员），它会连续发起多次tool_call
  4. 结果回传：工具执行完的结果会作为"tool"角色消息追加到对话历史中，LLM基于这些结果继续推理

03工具注册与描述

ToolUseSkill通过register_tool()方法注册工具。每个工具需要提供三个核心信息：

工具注册三要素
• name：工具名称，LLM通过这个名字发起调用（如"query_order"）
• description：工具描述，告诉LLM这个工具是干什么的（如"查询订单状态、物流信息"）
• parameters：参数定义，JSON Schema格式，告诉LLM每个参数的类型和含义

看一下_register_default_tools()方法注册的三个默认工具：

Python
def _register_default_tools(self):
    self.register_tool(
        name="query_order",
        description="查询订单状态、物流信息",
        parameters={
            "type": "object",
            "properties": {
                "order_id": {"type": "string", "description": "订单号"},
                "phone": {"type": "string", "description": "手机号"}
            }
        },
        handler=self._query_order_handler
    )
    self.register_tool(
        name="query_faq",
        description="查询常见问题解答",
        parameters={
            "type": "object",
            "properties": {
                "question": {"type": "string", "description": "问题内容"}
            }
        },
        handler=self._query_faq_handler
    )
    self.register_tool(
        name="get_user_info",
        description="获取用户会员等级、历史订单等信息",
        parameters={
            "type": "object",
            "properties": {
                "user_id": {"type": "string", "description": "用户ID"}
            }
        },
        handler=lambda user_id: {"level": "VIP", "orders": 12}
    )

注意description的写法：它不是写给人看的，是写给LLM看的。LLM根据description判断什么时候该用这个工具。描述越清晰、越具体，LLM的选择就越准确。如果你写"获取信息"，LLM可能乱用；如果你写"获取用户会员等级、历史订单等信息"，LLM就知道什么时候该调用了。

register_tool的底层实现非常简单——就是存两个字典：

Python
def register_tool(self, name, description, parameters, handler):
    self.tools[name] = {
        "name": name,
        "description": description,
        "parameters": parameters
    }
    self.handlers[name] = handler

一个字典存工具描述（传给LLM），一个字典存handler（实际执行）。简单粗暴。

04多轮Tool Calling执行流程

Function Calling最厉害的地方就是多轮组合调用。下面用一个时序图展示完整的执行过程：

图2：多轮Tool Calling时序图

这个流程的几个要点：

  • LLM一次发起多个tool_call：它可以在一轮对话中决定调用多个工具，不需要你逐个询问
  • 每个tool_call独立执行：你的代码逐个执行每个工具，把结果作为"tool"角色消息返回
  • LLM汇总结果：等所有工具的结果都返回后，LLM再综合所有信息生成最终回复
  • 最多3轮循环：代码中限制了最多3轮，防止LLM陷入无限循环
Python
def execute(self, user_input, context):
    messages = context.get("history", [])
    tools_schema = list(self.tools.values())

    for _ in range(3):
        result = self.llm.chat(messages, tools=tools_schema)

        if not result.get("tool_calls"):
            content = result.get("content", "")
            if content:
                return SkillResult(success=True, response=content, confidence=0.7)
            break

        tool_calls = result.get("tool_calls", [])
        messages.append({
            "role": "assistant",
            "content": result.get("content", ""),
            "tool_calls": tool_calls
        })

        for tc in tool_calls:
            tool_name = tc.get("name", "")
            tool_args = tc.get("arguments", {})
            tool_result = self.execute_tool(tool_name, tool_args)
            messages.append({
                "role": "tool",
                "tool_call_id": tc.get("id", "call_0"),
                "content": json.dumps(tool_result, ensure_ascii=False)
            })

    return SkillResult(success=False, response="", confidence=0.0)

核心逻辑就是一个for循环：把工具列表给LLM → LLM如果发起调用就执行 → 结果回传 → 再来一轮 → 直到LLM不再发起调用，或者达到3轮上限。

05工具执行与异常处理

execute_tool方法是工具调用的最后一环——根据名字找到handler，执行，返回结果：

Python
def execute_tool(self, name, args):
    if name not in self.handlers:
        return {"success": False, "error": f"未知工具: {name}"}
    try:
        result = self.handlers[name](**args)
        return {"success": True, "result": result}
    except Exception as e:
        return {"success": False, "error": str(e)}

异常处理的思路很明确：永远不要让工具异常中断整个流程。即使某个工具调用失败了，也返回一个带error字段的结果，让LLM决定如何处理（是告知用户，还是换个方式）。

为什么不让异常直接抛出？
假设用户同时查订单和查会员，订单查询成功了，但会员查询因为数据库超时失败了。如果异常直接抛出，用户什么信息都得不到。

但如果你捕获了异常，返回{"success": False, "error": "数据库超时"}，LLM拿到这个结果后，可以说"订单已经查到了，但会员信息暂时无法获取"——用户至少能拿到部分结果。

这就是降级优雅的思想：一个工具失败不影响其他工具的结果。

07设计要点与避坑指南

最后总结一下Function Calling的核心设计要点和常见坑：

✅ 要做的
• 工具描述写清楚：告诉LLM工具的使用场景和参数含义
• 异常优雅降级：工具失败返回error结果，不要抛异常
• 限制循环轮数：最多3轮，防止LLM陷入死循环
• 结果结构化：工具返回JSON，方便LLM理解
• 幂等设计：同一个tool_call_id对应一次执行，防止重复调用
❌ 不要做的
• 不要把工具当成函数库：工具是给LLM用的，不是给你代码用的
• 不要依赖LLM的参数格式：用JSON Schema严格定义参数类型
• 不要让LLM决定一切：高风险操作（如退款、修改订单）需要二次确认
• 不要忽略token消耗：多轮调用会消耗大量token，注意控制轮数
• 不要把Function Calling当银弹：简单场景用传统路由更高效

总结一下：Function Calling的本质是把工具调用的决策权从代码转移到LLM。通过给LLM提供工具的"说明书"，让它根据用户意图自主选择调用哪些工具、传什么参数、组合几次调用。

这给你的Agent装上了"双手"——不再是只能按预设流程回复的客服机器人，而是能根据实际需求灵活操作的智能助手。

但记住：LLM做决策，你做兜底。高风险操作必须加人工审核，这是客服场景的基本原则。
