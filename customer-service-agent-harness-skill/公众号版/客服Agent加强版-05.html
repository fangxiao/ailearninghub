FAQ检索：关键词和向量为啥都不能少

用户问："怎么改密码？"客服机器人："抱歉，我不太理解您的问题。"用户又问："如何修改账户密码？"客服机器人秒回："修改密码步骤：1.登录账户 2.进入账户设置 3.点击修改密码"——同样的意思，换个说法就不认得了？这就是单纯关键词检索的尴尬。

真正的检索不是字字匹配，而是心意相通。FAQ查询是客服Agent的第二大场景。单纯的关键词检索"不够聪明"，单纯的向量检索又"不够确定"。本篇介绍FAQ Skill如何用向量+关键词混合检索实现精准问答，以及LLM兜底降级策略——就像查字典，光会拼音不够，还得会按意思找。

💡 如果你看过之前的《客服Agent实战系列》，应该熟悉FAQ检索的基础方案。本篇是加强版，我们来聊聊怎么把单纯的检索升级成真正的生产级双引擎架构。

01为啥单引擎不够用？

先看两个真实的客服场景：

场景一：用户问"怎么开发票"
关键词检索：能命中"开发票"这个关键词，返回"如何申请发票"的FAQ——成功
向量检索：理解"开发票"≈"申请发票"，语义匹配成功——成功
场景二：用户问"那个东西开了吗"
关键词检索：完全匹配不上任何FAQ关键词——失败
向量检索：能理解"开了吗"可能指"发货了吗"，但置信度只有60%——不稳定

看到没？关键词检索擅长精确匹配，但遇到同义表达就傻眼。向量检索擅长语义理解，但遇到专有名词（比如订单号、产品型号）就不靠谱。

我在项目里试过纯向量检索，结果发现用户问"iPhone 15 Pro Max 256G有货吗"，向量检索把"Pro Max"理解成"专业版"，匹配到了完全不相关的FAQ。专有名词的精度，向量模型真的不如关键词匹配。

02双引擎检索架构

所以我们设计了HybridRetriever混合检索器，两个引擎并行跑，结果合并打分：

图1：双引擎检索架构

这个架构的核心思想是：各取所长，互补短板。

维度 关键词检索 向量检索
擅长场景 专有名词、精确匹配 同义表达、模糊语义
不擅长 语义变形、口语化表达 精确字符串、编号类查询
响应速度 快（毫秒级） 较慢（需计算向量）
可解释性 高（命中了具体关键词） 低（黑盒语义匹配）

03HybridRetriever实现

来看看核心代码怎么写的：

Python
class HybridRetriever:
    def __init__(self, faq_data, embedding_model):
        self.bm25 = BM25Retriever(faq_data)
        self.vector = VectorRetriever(embedding_model)
        self.faq_data = faq_data
        self.alpha = 0.6

    def search(self, query, top_k=3):
        keyword_results = self.bm25.search(query, top_k=10)
        vector_results = self.vector.search(query, top_k=10)

        fused = self._fuse_scores(
            keyword_results, vector_results
        )
        results = sorted(fused, key=lambda x: x['score'], reverse=True)

        return results[:top_k]

    def _fuse_scores(self, kw_results, vec_results):
        score_map = {}
        for item in kw_results:
            idx = item['index']
            score_map[idx] = {
                'index': idx,
                'score': item['score'] * self.alpha,
                'source': 'keyword'
            }
        for item in vec_results:
            idx = item['index']
            if idx in score_map:
                score_map[idx]['score'] += (
                    item['score'] * (1 - self.alpha)
                )
                score_map[idx]['source'] = 'hybrid'
            else:
                score_map[idx] = {
                    'index': idx,
                    'score': item['score'] * (1 - self.alpha),
                    'source': 'vector'
                }
        return list(score_map.values())

关键点在_fuse_scores方法：用alpha权重融合两路分数。默认0.6偏向关键词检索，你可以根据业务场景调整——如果FAQ中口语化问题多，就调低点alpha。

实战经验：我们在电商场景测试过，alpha=0.6时，FAQ命中率从单引擎的72%提升到94%。如果你的业务有很多专有名词（如产品型号、活动代号），建议alpha调到0.7。

04三级降级策略

再强的检索也有翻车的时候。比如用户问的问题FAQ里根本没有，或者两个引擎都没找到合适答案。这时候怎么办？

我们设计了三级降级策略，确保任何情况下都能给用户一个回应：

第一级：高置信度命中（score > 0.8）
直接返回FAQ标准答案，附带来源引用。用户体验最好的情况。
第二级：低置信度命中（0.5 < score < 0.8）
把Top-3的FAQ片段丢给LLM，让它基于这些候选生成一个更自然的回答。同时标注"参考了以下内容"，增加可信度。
第三级：LLM兜底（score < 0.5）
FAQ没找到相关内容，直接走LLM对话模式。但要给LLM加约束："如果不确定，请建议用户转人工客服"——别让AI瞎编答案。

图2：三级降级流程

这里有个坑：第三级如果完全放开LLM，它可能会编造FAQ里没有的政策。我们的做法是给LLM一个system prompt约束："你是客服助手，只能基于提供的FAQ内容回答。如果FAQ里没有相关信息，请回复'这个问题我需要转接人工客服来处理'。"宁可承认不知道，也不能瞎编。

05FAQ Skill完整流程

把上面这些串起来，就是完整的FAQ Skill处理流程：

Python
class FAQSkill(BaseSkill):
    name = "faq"
    priority = 2

    def execute(self, context):
        retriever = context.get_retriever()
        query = context.user_message

        results = retriever.search(query, top_k=3)

        if results[0]['score'] > 0.8:
            return self._direct_answer(results[0])
        elif results[0]['score'] > 0.5:
            candidates = [r['content'] for r in results]
            return self._llm_based_answer(candidates, query)
        else:
            return self._llm_fallback_answer(query)

    def _direct_answer(self, result):
        return {
            'type': 'faq_answer',
            'content': result['answer'],
            'source': result['faq_id'],
            'confidence': result['score']
        }

    def _llm_based_answer(self, candidates, query):
        prompt = f"""基于以下FAQ内容回答用户问题：
        候选内容：{candidates}
        用户问题：{query}
        如果候选内容不够，请说明需要更多信息。"""
        response = self.llm.generate(prompt)
        return {
            'type': 'llm_answer',
            'content': response,
            'confidence': 0.7
        }

    def _llm_fallback_answer(self, query):
        prompt = f"""你是客服助手，回答用户问题。
        如果不确定，请建议转人工。
        用户问题：{query}"""
        response = self.llm.generate(prompt)
        return {
            'type': 'fallback_answer',
            'content': response,
            'confidence': 0.3
        }

这个Skill的设计遵循了Harness架构的核心原则：每个Skill只管自己的事，检索策略可替换，降级策略可配置。

06性能优化小贴士

  1. 向量缓存：FAQ的embedding预先计算好存Redis，别每次搜索都重新算
  2. 热词缓存：高频问题的答案直接缓存，跳过检索过程
  3. 超时控制：向量检索设200ms超时，超时直接走关键词检索降级
  4. 日志埋点：记录每次检索的分数和命中来源，持续优化alpha权重

我们把这些优化都做了之后，FAQ检索的P99延迟从800ms降到了120ms，命中率稳定在94%以上。双引擎+三级降级，是生产级FAQ检索的标配。
