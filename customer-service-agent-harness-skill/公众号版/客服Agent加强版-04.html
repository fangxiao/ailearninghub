OrderSkill：订单查询的正确姿势

上周看一个同事的 bot.py，500行代码里有200行是订单查询的 if/else：解析订单号一个if，解析手机号一个if，查物流一个if，错误处理一个if……改一个需求，要动主循环；加一个查询类型，要改半壁江山。更要命的是，订单查询的逻辑和意图识别、情感分析混在一起，代码里全是交叉引用——牵一发而动全身。

真正的高手不是把代码写得多，而是把代码拆得干净。订单查询是客服场景中最高频的需求之一。本篇以 OrderSkill 为例，完整展示从V1插件到V2 Skill的升级过程——就像把一堆散乱的杂物塞进抽屉盒，每个抽屉各司其职，拉出来就能用。

💡 如果你看过之前的《客服Agent实战系列》，应该熟悉V1的订单插件实现。本篇是加强版第四篇，我们来看看在 Harness+Skill 架构下，订单查询能变得多么优雅。

1先看V1订单插件的"烂摊子"

在V1插件架构里，订单查询是这样写的——所有逻辑塞在一个 OrderPlugin 类里，由 Bot 主循环直接调用：

Python
# V1 订单插件 - 典型的"大杂烩"写法
class OrderPlugin:
    def handle(self, user_input, context):
        if "订单" in user_input or "物流" in user_input:
            if "订单号" in user_input:
                order_id = self._extract_order_id(user_input)
                if order_id:
                    return self._query_by_order_id(order_id)
                else:
                    return "请提供正确的订单号"
            elif "手机" in user_input or re.search(r'1[3-9]\d{9}', user_input):
                phone = self._extract_phone(user_input)
                if phone:
                    return self._query_by_phone(phone)
                else:
                    return "请提供正确的手机号"
            else:
                # 模糊查询 - 又一坨if/else
                if context.get("user_id"):
                    return self._query_user_orders(context["user_id"])
                else:
                    return "请提供订单号或手机号"
        else:
            return None  # 不是订单相关，返回None

这段代码有什么问题？表面上看功能齐全，实际上：

  • 耦合严重：解析、查询、格式化混在一起，改一处动全身
  • 无标准接口：返回值是字符串或None，Bot主循环需要硬编码判断
  • 无法独立测试：要测订单查询，必须先初始化整个Bot
  • 无法动态扩展：想加个"退款查询"？又要加if/else

这就是V1的通病：插件看起来是解耦的，实际上是"换了个地方耦合"。主循环依赖插件的返回格式，插件依赖主循环的上下文结构，彼此纠缠不清。

2OrderSkill 的 can_handle 打分机制

进入V2 Skill架构后，一切都变了。首先看 can_handle——这是Router选择Skill的唯一依据，也是OrderSkill的"自我推荐信"：

Python
class OrderSkill(BaseSkill):
    @property
    def name(self) -> str:
        return "order"

    @property
    def triggers(self) -> List[str]:
        return ["订单", "物流", "发货", "配送", "快递", "到哪", "状态", "查单"]

    @property
    def priority(self) -> int:
        return 9  # 高优先级

    def can_handle(self, user_input: str, context: dict) -> float:
        score = super().can_handle(user_input, context)
        # 加权：如果意图明确是订单查询，直接给高分
        if context.get("intent") == "order_query":
            score = max(score, 0.9)
        return score

来看看 can_handle 的打分逻辑：

用户输入命中trigger基础分加权条件最终分
"订单号2024001查一下""订单" 命中0.6intent="order_query" → +0.30.9
"我的快递到哪了""快递" 命中0.6无明确intent0.6
"今天天气不错"无命中0.0无0.0
"查下物流状态""物流" + "状态" 命中0.6intent="order_query" → +0.30.9

设计哲学：can_handle 不是"是或否"的判断题，而是"有多大把握"的置信度评分。这让Router可以在多个Skill之间做排序选择，而不是"有就上"的粗粒度匹配。数值化的打分，是路由决策从"拍脑袋"到"讲道理"的关键一步。

3OrderSkill 的 execute 执行流程

被Router选中后，OrderSkill.execute() 开始干活。整个流程分为五步：参数提取 → 订单搜索 → 结果格式化 → 返回SkillResult → 异常处理。

图1：OrderSkill execute 执行流程

对应到代码实现：

Python
def execute(self, user_input: str, context: dict) -> SkillResult:
    # 步骤1：提取参数
    order_id = self._extract_order_id(user_input)
    phone = self._extract_phone(user_input)

    # 步骤2：参数缺失时，从context.slots补充
    if not order_id and not phone:
        slots = context.get("slots", {})
        if slots.get("order_id"):
            order_id = slots["order_id"]
        else:
            return SkillResult(
                success=False,
                response="请提供订单号或手机号，我帮您查询。",
                confidence=0.5
            )

    # 步骤3：搜索订单
    orders = self._search_orders(order_id, phone)

    # 步骤4：未找到时返回失败
    if not orders:
        return SkillResult(
            success=False,
            response="未找到相关订单，请确认信息是否正确。",
            confidence=0.6
        )

    # 步骤5：格式化并返回
    response = self._format_orders(orders)
    return SkillResult(
        success=True,
        response=response,
        data={"orders": orders},
        confidence=0.9
    )

4真实订单查询示例

光说不练，来看一次真实的对话过程。用户输入："订单号 SF20240601001 到哪了？"

执行过程追踪
① Router 路由阶段
- 意图识别输出：intent = "order_query"
- Router 精确匹配：order_query → OrderSkill
- can_handle 打分：基础分 0.6 + intent加权 0.3 = 0.9
- 命中 OrderSkill

② OrderSkill 执行阶段
- _extract_order_id() 用正则匹配：订单[号]?[:\s]*([a-zA-Z0-9]{6,})
- 提取出 order_id = "SF20240601001"
- _search_orders("SF20240601001", None) 查询订单
- 找到订单，_format_orders() 格式化为自然语言

③ 返回结果
SkillResult(success=True, response="您的订单 SF20240601001：配送中（玫瑰花束），预计明天 18:00 前送达，物流单号：SF123456", data={"orders": [...]}, confidence=0.9)

再看一个边界场景——用户只说了"查一下我的订单"，没给订单号：

参数缺失时的优雅降级
- _extract_order_id() 返回 None
- _extract_phone() 返回 None
- 检查 context.slots，如果有历史订单号则使用
- 如果 slots 也为空，返回：
SkillResult(success=False, response="请提供订单号或手机号，我帮您查询。", confidence=0.5)
- Harness 拿到结果后，会把 response 直接返回给用户，同时把 confidence=0.5 标记为"需要追问"
- 对话管理器会在下一轮引导用户提供订单号

5V1 vs V2：订单实现的"三代升级"

把 V1 插件和 V2 Skill 放在一起对比，差异一目了然：

维度V1 订单插件V2 OrderSkill
接口标准handle() 返回 str/Nonecan_handle() + execute() 返回 SkillResult
路由方式Bot主循环硬编码 if/elseRouter三策略自动打分路由
参数提取散落在 handle 内部独立私有方法 _extract_order_id / _extract_phone
错误处理返回错误字符串，主循环判断返回 SkillResult(success=False)，统一处理
可测试性必须初始化整个Bot可独立实例化测试
可扩展性加查询类型要改handle新增私有方法即可，execute不动
数据传递纯文本，数据丢失response + data 双通道，保留结构化数据

最大的变化不是代码风格，而是设计哲学的转变。V1是"面向流程编程"——主流程牵着插件走；V2是"面向能力编程"——每个Skill独立声明能力，Router按需调度。从"你要我做什么"到"我能做什么"，这才是架构升级的本质。

6SkillResult：不只是返回值

OrderSkill.execute() 返回的 SkillResult 是整个Skill体系的"通用语言"。来看它的字段设计：

Python
@dataclass
class SkillResult:
    success: bool = True          # 是否成功
    response: str = ""           # 给用户的回复文本
    data: dict = field(default_factory=dict)  # 结构化数据（订单详情等）
    next_action: str = None       # 建议的下一步动作
    confidence: float = 0.0       # 处理置信度
    need_handoff: bool = False    # 是否需要转人工
    error: str = None             # 错误信息
场景successconfidence其他关键字段Harness 行为
正常查询命中True0.9data 含订单直接回复用户
参数缺失False0.5response 提示补充追问用户
订单不存在False0.6response 提示确认重试或引导
系统异常False0.1error 含异常降级/转人工
需要人工True0.4need_handoff=True触发转人工流程

confidence 是最被低估的字段。它不是"处理的把握"，而是"让上游决策的信号"。低 confidence 告诉 Harness："我不确定处理对了，你看着办——要么追问用户，要么找别的Skill，要么转人工。" 这让整个系统可以实现自信度驱动的多轮对话，而不是单次命中式的"一问一答"。

7本篇总结

核心要点：

1. can_handle 是"自我推荐信"：不是布尔判断，而是0-1的置信度评分，支持加权

2. execute 是"五步流水线"：提取参数 → 补充参数 → 搜索 → 格式化 → 返回

3. SkillResult 是"通用语言"：7个字段覆盖成功/失败/追问/转人工等所有场景

4. V1→V2 是哲学升级：从"面向流程"到"面向能力"，从"你要我做"到"我能做"

5. confidence 是"协调信号"：低置信度触发追问/转人工，实现多轮对话
