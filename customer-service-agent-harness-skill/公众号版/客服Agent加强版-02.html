客服Agent进化论 ②

BaseSkill：给Agent发张身份证

你见过多少插件系统？每个插件的接口都不一样——有的叫 execute()，有的叫 handle()，有的叫 process()。返回值也千奇百怪：有的返回字符串，有的返回 dict，有的直接返回 None。结果就是调度器变成了 if/else 地狱，每加一个插件就要改一遍主循环。

这就是V1版本的痛点。没有标准接口的系统，就像没有交通规则的马路——每个人都按自己的理解开车，迟早撞成一团。

本篇就来聊聊Harness+Skill架构的基石——BaseSkill 抽象类和 SkillResult 数据类。它们是所有Skill的身份证和劳动合同，定义了Skill能做什么、不能做什么、必须做什么。

💡 如果你看过之前的《客服Agent实战系列》，应该熟悉V1插件架构。本篇是加强版第二篇，我们来聊聊Harness+Skill架构的基石——BaseSkill标准接口。

1为什么需要标准接口？

先看V1的问题。假设我们有三个插件，每个插件的写法都不一样：

Python
# V1：三个插件，三种风格
class FAQPlugin:
    def answer(self, question):
        # 返回字符串
        return "您的问题答案是..."

class OrderPlugin:
    def query(self, text, user_id):
        # 返回 dict
        return {"status": "success", "data": {...}}

class SentimentPlugin:
    def analyze(self, text):
        # 直接修改全局变量，不返回值
        global sentiment_score
        sentiment_score = 0.8
        return None

当Harness（当时叫Bot）要调用这些插件时，代码变成了：

Python
# V1调度器的灾难
def process(self, user_input):
    if intent == "faq":
        result = self.faq_plugin.answer(user_input)
        response = result  # 直接用字符串
    elif intent == "order":
        result = self.order_plugin.query(user_input, user_id)
        if result["status"] == "success":
            response = result["data"]  # 要取data字段
    elif intent == "sentiment":
        self.sentiment_plugin.analyze(user_input)
        response = f"情感分：{sentiment_score}"  # 依赖全局变量
    
    # 每加一个插件，这里就要改！

没有标准接口的后果：

1. 调度器膨胀 —— 每个插件的调用方式都不同，调度器里全是if/else
2. 无法扩展 —— 想加新插件？先看清楚现有插件的返回格式
3. 难以测试 —— 每个插件的测试方式都不一样，Mock困难
4. 错误处理混乱 —— 有的插件抛异常，有的返回None，有的返回空字符串

所以我们需要一套标准接口，让所有Skill都遵守同一个"合同"：

  • 所有Skill都有相同的属性（name、description、triggers、priority）
  • 所有Skill都实现相同的方法（can_handle、execute、on_error）
  • 所有Skill都返回相同的数据结构（SkillResult）

2SkillResult：Skill的标准返回值

先看返回值。如果说Skill是员工，那SkillResult就是员工提交的工作报告。无论做什么工作，报告的格式是统一的。

Python
from dataclasses import dataclass, field
from typing import Dict, List, Any, Optional

@dataclass
class SkillResult:
    success: bool = True
    response: str = ""
    data: Dict[str, Any] = field(default_factory=dict)
    next_action: Optional[str] = None
    confidence: float = 0.0
    need_handoff: bool = False
    error: Optional[str] = None

每个字段的含义：

字段类型含义示例
successboolSkill是否成功执行True / False
responsestr返回给用户的文本"您的订单已发货"
dataDict附加数据，供其他Skill或Harness使用{"order_id": "xxx"}
next_actionstr建议的下一步动作"ask_order_id"
confidencefloat结果的置信度0.9
need_handoffbool是否需要转人工True / False
errorstr错误信息（失败时填写）"API调用超时"

图1：SkillResult的数据流向

注意 data 字段的作用——它是Skill之间通过Harness传递数据的唯一渠道。比如FAQ Skill可以把检索到的FAQ ID放在data里，供后续的Memory Skill记录。

这就是为什么我说它是"劳动合同"——Skill之间不能直接通信，必须通过SkillResult.data这个公共通道。

3BaseSkill：所有Skill的抽象基类

有了统一的返回值，我们就能定义统一的接口了。来看 base.py 的完整代码：

Python
from abc import ABC, abstractmethod
from dataclasses import dataclass, field
from typing import Dict, List, Any, Optional

@dataclass
class SkillResult:
    success: bool = True
    response: str = ""
    data: Dict[str, Any] = field(default_factory=dict)
    next_action: Optional[str] = None
    confidence: float = 0.0
    need_handoff: bool = False
    error: Optional[str] = None


class BaseSkill(ABC):
    """Skill标准接口 - 所有客服技能的抽象基类"""

    @property
    @abstractmethod
    def name(self) -> str:
        """技能名称"""
        ...

    @property
    @abstractmethod
    def description(self) -> str:
        """技能描述"""
        ...

    @property
    def triggers(self) -> List[str]:
        """触发关键词/模式"""
        return []

    @property
    def priority(self) -> int:
        """优先级（数值越大越优先）"""
        return 1

    @property
    def pre_skill(self) -> bool:
        """是否为前置Skill（在主流程前执行）"""
        return False

    def can_handle(self, user_input: str,
                   context: Dict[str, Any]) -> float:
        """评估该技能处理用户输入的置信度"""
        if not self.triggers:
            return 0.0
        score = 0.0
        for trigger in self.triggers:
            if trigger.lower() in user_input.lower():
                score = max(score, 0.6)
                if trigger == user_input:
                    score = max(score, 0.9)
        return score

    @abstractmethod
    def execute(self, user_input: str,
                context: Dict[str, Any]) -> SkillResult:
        """执行技能，返回SkillResult"""
        ...

    def on_error(self, error: Exception,
                 context: Dict[str, Any]) -> SkillResult:
        """降级处理 - 技能执行失败时调用"""
        return SkillResult(
            success=False,
            response="抱歉，处理您的请求时出现了问题，请稍后再试。",
            error=str(error)
        )

    def get_info(self) -> Dict[str, Any]:
        """获取技能信息"""
        return {
            "name": self.name,
            "description": self.description,
            "triggers": self.triggers,
            "priority": self.priority,
            "pre_skill": self.pre_skill,
        }

我们来拆解一下这个抽象类的设计。

4必填属性 vs 可选属性

BaseSkill把属性分成了两类：

类型属性说明
必须实现nameSkill唯一标识，如 "faq"、"order"
descriptionSkill描述，用于日志和调试
可选覆盖triggers触发关键词列表，用于can_handle打分
priority优先级，数值越大越优先（默认1）
pre_skill是否为前置Skill（默认False）

来看看FAQ Skill是怎么实现这些属性的：

Python
class FAQSkill(BaseSkill):
    @property
    def name(self) -> str:
        return "faq"

    @property
    def description(self) -> str:
        return "FAQ Skill - 基于知识库回答用户常见问题"

    @property
    def triggers(self) -> List[str]:
        return ["密码", "退款", "配送", "支付",
                "发货", "怎么", "如何", "多久", "修改", "申请"]

    @property
    def priority(self) -> int:
        return 7  # 比默认的1高很多

    # pre_skill 保持默认 False

    def can_handle(self, user_input, context):
        # 覆盖基类方法，增加意图权重
        score = super().can_handle(user_input, context)
        if context.get("intent") == "faq_query":
            score = max(score, 0.85)
        return score

    def execute(self, user_input, context):
        # ... 业务逻辑
        pass

注意FAQ Skill覆盖了 can_handle 方法——它在基类打分的基础上，增加了意图权重。这就是"模板方法模式"的好处：基类提供默认实现，子类可以按需覆盖。

5can_handle：Skill的自我评估机制

can_handle() 是BaseSkill最精巧的设计之一。它回答一个问题："这个Skill有多大把握处理当前请求？"

图2：can_handle打分机制

打分逻辑分三层：

分数含义场景
0.0完全不匹配Skill没有trigger，或trigger完全不匹配
0.6部分匹配trigger在用户输入中出现
0.9高度匹配用户输入完全等于某个trigger
自定义子类覆盖FAQ Skill根据意图加到0.85

Router会收集所有Skill的分数，选择得分最高的那个。如果最高分低于0.3，就走兜底逻辑。

6execute：Skill的核心执行流程

execute() 是Skill的业务核心。基类只定义了接口签名，具体逻辑完全由子类实现。来看FAQ Skill的execute实现：

Python
class FAQSkill(BaseSkill):
    def execute(self, user_input: str,
                context: Dict[str, Any]) -> SkillResult:
        # 1. 混合检索（关键词 + 向量）
        results = self._hybrid_search(user_input)

        # 2. 有结果直接返回
        if results:
            return SkillResult(
                success=True,
                response=results[0]["answer"],
                data={"faq_results": results},
                confidence=results[0].get("score", 0.5)
            )

        # 3. 没结果，LLM兜底
        if self.llm.is_available():
            llm_response = self._llm_fallback(user_input)
            if llm_response:
                return SkillResult(
                    success=True,
                    response=llm_response,
                    data={"source": "llm_fallback"},
                    confidence=0.6
                )

        # 4. 彻底失败
        return SkillResult(
            success=False,
            response="抱歉，暂时无法回答这个问题。"
                     "您可以转人工客服咨询。",
            confidence=0.2
        )

注意execute的几个要点：

  • 始终返回SkillResult —— 无论成功失败，永远返回SkillResult对象
  • 用success字段表示结果 —— 成功时success=True，失败时success=False
  • 错误时也要有response —— 即便是失败，也要给用户一个友好的回复
  • confidence反映把握 —— 检索命中时高，LLM兜底时中，彻底失败时低

7on_error：优雅的降级处理

即便有了标准接口，Skill还是可能出错。LLM API超时、数据库连接失败、依赖服务不可用……这些异常都不应该让整个Harness崩溃。

这就是 on_error() 的作用——给Skill一个"兜底"的机会：

Python
# BaseSkill的默认on_error实现
def on_error(self, error: Exception,
             context: Dict[str, Any]) -> SkillResult:
    return SkillResult(
        success=False,
        response="抱歉，处理您的请求时出现了问题，"
                 "请稍后再试。",
        error=str(error)
    )

Harness在执行Skill时，会用try/except包裹：

Python
# harness.py 中的异常处理
try:
    result = skill.execute(user_input, context)
except Exception as e:
    # 调用Skill的on_error降级
    result = skill.on_error(e, context)
    # 记录熔断器
    self.breaker.record_failure(skill.name)
    # 尝试兜底
    fallback = self.registry.get_skill("general")
    if fallback and fallback.name != skill.name:
        result = fallback.execute(user_input, context)

三级降级策略：

1. 第一级：Skill自己的on_error——返回一个友好的错误提示
2. 第二级：Harness的兜底Skill（GeneralSkill）——用LLM做通用回复
3. 第三级：硬编码的"系统繁忙"——确保至少有响应返回给用户

8Skill完整示例：一个问候Skill的诞生

把今天学的知识串起来，看一个完整的Skill是怎么写的：

Python
class GreetingSkill(BaseSkill):
    """问候Skill - 处理打招呼、再见等寒暄"""

    def __init__(self, config, memory):
        self.config = config
        self.memory = memory

    @property
    def name(self) -> str:
        return "greeting"

    @property
    def description(self) -> str:
        return "问候Skill - 处理打招呼、再见等寒暄"

    @property
    def triggers(self) -> List[str]:
        return ["你好", "您好", "hi", "hello",
                "再见", "拜拜", "谢谢", "感谢"]

    @property
    def priority(self) -> int:
        return 5

    def can_handle(self, user_input, context):
        score = super().can_handle(user_input, context)
        # 问候类意图加分
        if context.get("intent") in ("greeting", "thanks"):
            score = max(score, 0.8)
        return score

    def execute(self, user_input, context):
        user_id = context.get("user_id", "anonymous")
        user_summary = self.memory.get_user_summary(user_id)

        # 根据用户历史生成不同的问候
        if user_summary.get("first_seen"):
            response = f"欢迎回来！{user_summary.get('nickname', '')}"
        else:
            response = "您好！我是客服助手，" \
                       "请问有什么可以帮您？"

        if any(w in user_input for w in ["再见", "拜拜"]):
            response = "再见，祝您生活愉快！"

        return SkillResult(
            success=True,
            response=response,
            data={"skill": "greeting", "user_id": user_id},
            confidence=0.9
        )

    def on_error(self, error, context):
        return SkillResult(
            success=False,
            response="您好，我是客服助手，请问有什么可以帮您？",
            error=str(error)
        )

一个完整的Skill就这样诞生了。没有if/else，没有硬编码，完全遵守BaseSkill的标准接口。

9本篇总结：BaseSkill的设计哲学

BaseSkill的三个设计哲学：

1. 约定优于配置
所有Skill必须实现name和description，其他属性有合理默认值。写一个新Skill的成本极低——通常只需实现2个属性 + 2个方法。

2. 数据优于控制
Skill之间通过SkillResult.data传递信息，而不是直接调用。这种松耦合设计让Skill可以独立开发、独立测试。

3. 防御优于乐观
on_error降级、success状态、兜底Skill——每一层都在为最坏情况做准备。一个Skill的失败不应该影响整个系统。
