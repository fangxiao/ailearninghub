AI 其实会写测试，问题在没人逼它先写。TDD Skills 就是干这件事的——一个 Claude Code 插件，强制 AI 走 RED-GREEN-REFACTOR 循环，不写测试不让写代码。

一句话总结：morodomi 开源的 Claude Code 插件，用强制 TDD 流程让 AI 老老实实先写测试，再写实现。

01 TDD Skills 是什么

TDD Skills 是开发者 morodomi 开源的 Claude Code 插件，当前版本 v5.1.1。它做的事情很简单，也很硬核——把 TDD（测试驱动开发）流程做成 AI 跳不过去的强制步骤。

🎯 核心理念：不写测试不让写代码。AI 想动实现代码，必须先有一个失败的测试。

🔄 强制循环：RED（写失败测试）→ GREEN（最小实现通过）→ REFACTOR（重构优化），三阶段顺序不可跳过。

🧠 Agent Memory：审查者角色跨会话积累项目知识，测试规范、架构决策自动沉淀，下次直接复用。

📋 阶段守卫：每个阶段有明确入口和出口检查，AI 不能自说自话跳到下一步。

换句话说，它不是"建议"AI 写测试，而是把测试做成写代码的前置条件。AI 想"完成"功能，必须先证明测试跑通，否则流程不结束。

1 添加插件市场

💡 验证安装

装完输入 /tdd-skills:start 试试。如果出现 TDD 流程引导，说明安装成功。

03 TDD 循环详解：RED → GREEN → REFACTOR

TDD Skills 把测试驱动开发拆成三个强制阶段，AI 必须按顺序走完，谁也不能跳步：

🔴 RED 阶段：先写失败的测试

AI 根据需求生成测试用例，运行后必须看到测试失败。这一步证明两件事：测试本身有效，且功能还没实现。

关键动作：AI 分析需求 → 列出测试用例 → 生成测试代码 → 运行确认失败 → 进入下一阶段。

🟢 GREEN 阶段：写最小实现让测试通过

AI 写最少的实现代码让测试转绿。注意是"最小"，不是"最优"——这一步禁止过度设计，目标是让测试通过即可。

关键动作：编写实现代码 → 运行测试 → 全部通过 → 锁定绿态 → 进入下一阶段。

🔵 REFACTOR 阶段：重构优化，测试必须仍然通过

AI 优化代码结构、消除重复、提升可读性，但测试必须始终是绿的。一旦测试变红，重构立即停止，回滚到上一步。

关键动作：识别坏味道 → 重构代码 → 重跑测试 → 确认仍通过 → 完成循环。

💡 为什么强制顺序这么重要？

不强制的 TDD 等于没有 TDD。AI 一旦被允许"先写代码再补测试"，就会本能地写一些迎合实现代码的弱测试，覆盖率好看但抓不到 bug。强制 RED 在前，逼着 AI 先想清楚"这个功能该满足什么行为"，再动手写实现。

04 核心命令

TDD Skills 提供三个核心命令，对应流程的启动和阶段切换：

🚀 三个核心命令

启动 TDD 流程，告诉 AI 接下来按 TDD 规则干活：

/tdd-skills:start # 启动 TDD 流程

进入 RED 阶段，AI 生成失败测试用例：

/tdd-skills:red # 进入 RED 阶段

进入 GREEN 阶段，AI 写最小实现让测试通过：

/tdd-skills:green # 进入 GREEN 阶段

用法很简单：先 /tdd-skills:start 启动流程，然后用 /tdd-skills:red 和 /tdd-skills:green 切换阶段。AI 会在每个阶段做对应的检查，不通过不让走。

05 实战演示：开发一个用户注册功能

看一次完整流程最直观。假设要开发一个"用户注册"功能，看看 TDD Skills 怎么接管整个循环：

1 RED：输入 /tdd-skills:red 生成失败测试

你输入："开发用户注册功能，邮箱+密码"

AI 生成测试用例：

  • 注册成功：合法邮箱+合法密码 → 返回用户 ID
  • 邮箱重复：已注册邮箱 → 抛出冲突错误
  • 邮箱格式非法：缺 @ → 抛出校验错误
  • 密码过短：少于 8 位 → 抛出校验错误

▶ 运行测试：4 个全失败（功能还没实现）✅ 进入 GREEN

2 GREEN：输入 /tdd-skills:green 写最小实现

AI 写最少的实现代码：

  • 实现 register 函数：接收 email + password
  • 加邮箱格式正则校验
  • 加密码长度校验
  • 查重：查数据库是否已存在

▶ 运行测试：4 个全通过 ✅ 进入 REFACTOR

3 REFACTOR：AI 重构优化，测试必须保持绿

AI 识别可优化点并重构：

  • 把校验逻辑抽成独立的 validateInput 函数
  • 错误类型统一为 RegistrationError
  • 数据库查询加索引提示

▶ 重跑测试：4 个仍然全通过 ✅ 循环完成

💡 关键点

整个过程 AI 没机会跳过测试。RED 不失败不让进 GREEN，GREEN 不通过不让进 REFACTOR，REFACTOR 测试变红立即回滚。这就是"强制"的含义。

06 Agent Memory：跨会话知识积累

TDD Skills 除了强制流程，还有杀手锏：Agent Memory。它内置一个审查者角色，会跨会话积累项目知识。

🧠 自动沉淀：每次 TDD 循环中，审查者会记录项目的测试规范、命名约定、架构决策、常见陷阱。

🔄 跨会话复用：下次打开新对话，审查者带着之前的记忆上岗。你不用再重复说"我们用 Jest""测试文件放 __tests__ 目录"。

👀 持续审查：审查者会在每个阶段检查代码是否符合项目历史规范，发现偏离立即提醒。

📈 越用越准：项目越大、用得越久，审查者积累的知识越丰富，AI 的输出越贴合你的团队习惯。

这解决了 TDD 落地的一个老大难问题：每个新会话都得重新教 AI 项目规范。有了 Agent Memory，知识自动积累，AI 不再"失忆"。

07 与 Superpowers / ECC 的区别

很多人会问：Superpowers 和 ECC 也有 TDD 相关功能，TDD Skills 有什么不一样？一句话——专注度不同。

⚖️ 三者对比

vs Superpowers

Superpowers 包含 TDD 但更重，是一整套开发方法论。TDD Skills 专注 TDD 这一件事，轻量、专一、即装即用。

vs ECC 的 /tdd 命令

ECC 的 /tdd 命令是轻量触发，建议 AI 走 TDD 但可绕过。TDD Skills 是强制流程，不写测试不让写代码，跳不过去。

怎么选？

想要一站式工程能力 → ECC；想要完整开发方法论 → Superpowers；只想把 TDD 这件事做扎实 → TDD Skills。三者也可以搭配使用。

📖 延伸阅读

想了解 Superpowers 的完整开发流程，可以看这篇：《Superpowers：把 AI 编程从凭感觉变成按流程》。两者搭配用，流程 + 强制 TDD，效果更好。

08 3 个常见疑问

Q1：强制 TDD 会不会让 AI 变慢？

会慢一点，但慢在写测试上，省在 debug 上。前期多花 20% 时间写测试，后期少花 80% 时间修 bug。整体看是赚的，尤其在中大型项目里。

Q2：支持什么语言和测试框架？

语言层面不限制，TypeScript、Python、Go、Rust、Java 都能用。只要项目里有测试框架（Jest、Pytest、Go test、JUnit 等），AI 就能生成对应的测试代码。

Q3：能跳过测试吗？我想快速出原型的时候。

可以。不启动 /tdd-skills:start 就不会强制。但一旦启动了，就别想跳，这正是它的价值。建议：原型阶段不启动，正式开发阶段必启动。

✨ 写在最后

AI 写代码快，但不写测试的话，这个快没多大意义。TDD Skills 盯住的是"AI 不愿意先写测试"这个习惯。AI 不是不会写测试，是不肯排在前面写。强制 RED 在前，逼着它先把要满足的行为想清楚再动手，这是它和普通提示词最不一样的地方。

如果你受够了 AI 说"已完成"却没跑测试，可以装上这个插件试两轮。启动流程后它就按阶段走，想跳也跳不了，测试这道门槛会自动卡住它。
